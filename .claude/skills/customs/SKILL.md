> 마감: 2026-08-28 09:00 KST · 패턴: 대장형 · 갱신: 2026-08-15

## 한 줄 정의

뉴트리시아몰(자사몰)의 해외직구 주문을 관세청 전자상거래 전용 REST API v1.4.1로 신고하고, 그 데이터를 동수(중국 물류·ERP) · 자이언트(특송사) · NICE(개인통관고유부호 검증)와 어긋나지 않게 맞추는 4자 연동. 오픈 2026-08-28 09:00 KST.

## 절대 규칙

1. 협력사 공유 양식(`planning_v6.html` · `api_field_mapping.html`)은 **구조를 바꾸지 않는다.** 값·설명 정정만. 중문판은 동시에 정정한다.
2. 자이언트 규격은 Postman 화면으로 판단하지 않는다. **컬렉션 원본 JSON을 내려받아 대조한다.** 화면은 지연 로딩되어 일부만 보인다 (2026-08-10 1차 검토 오판 원인).
3. 관세청 필드는 **명세서 v1.4.1 원문과 대조한 값만** 쓴다. 기획 문서에 있다고 맞는 값이 아니다 — 실제로 필드명 5건이 틀려 있었다.
4. 리스크·결정·질의·협의 이력의 정본은 `planning/리스크_질의대장.html` 하나다. 다른 문서에 새로 적지 않는다. `[2026-08-13 정정] 종전 정본 risk_list.html → 리스크_질의대장.html (2026-08-12 커밋 330367f에서 통합·삭제).`
5. 협의가 생기면 **통합 대장에 먼저 한 줄** 추가하고 기획서에 반영한다. `planning/협의이력.html`은 채팅 원문 아카이브이며 **더 이상 갱신하지 않는다** — 두 문서가 다르면 통합 대장이 이긴다.
6. `documents/`의 PDF는 원본이다. 수정하지 않는다.

## 함정

**어느 원본 문서에도 없는 지식이다. 겪어야만 알 수 있어 재조사로 복구되지 않는다.**

**관세청 TRA**
- "오류 없음 = 성공"은 거짓이다. TRA002 하나가 성공·부분오류·전체반려를 모두 반환한다(`txif_prcs_stcd` 01/02/03 + `errors[]`). TRA003은 보조이며 **택일 관계**지 후속이 아니다. 단 **우리는 TRA002를 쓰지 않기로 했다** — 이 항목은 전환 재검토 시의 규격 사실이다.
- TRA002로 `0000`을 받은 제출번호는 TRA003에 나오지 않는다. "TRA002 → TRA003" 순차 호출은 항상 빈 값이다.
- `txif_rgsr_err_cnt`가 0이어도 상품 개별 오류가 있을 수 있다. `errors[]`를 반드시 확인한다.
- `3000`은 동일 `txif_sbmt_no` 중복이다. IP 차단이 아니다. 진짜 30분 규정은 PER001에서 `ord_no_icln_tp=01` 발급 시 30분 내 주문완료 의무.

**자이언트 GGATE**
- `POST /api/hwb/search`는 없는 `hwbNo`를 에러 없이 조용히 제외한다. `transportType`(AI/OI 필수)을 틀려도 같다. **"결과에 없음"과 "동수 미전송"이 구분되지 않는다.**
- 중복 등록은 `H006`. **DELETE 엔드포인트가 없다** — 기획서의 `DELETE /api/hwb/{hwbNo}`와 "미완성 HBL 24시간 자동 소멸"은 컬렉션에서 확인되지 않는다.
- `PATCH` 예시의 `consigneeTel`은 대시 포함(`010-4024-3740`)인데 관세청은 하이픈 제외다. 포맷 분기가 필요하다.
- 소수점 자릿수가 어긋난다. `unitPrice` 3자리 / `totalValueUsd` 2자리 / 관세청 (16,3).
- 문자열 길이는 기획 문서보다 자이언트가 짧다(`productName` 200 등). 대조표는 `documents/자이언트_API_메모.md` 4절.
- `weight`가 0이면 `H014`.
- `POST /api/hwb/search`는 최대 500건, 증설 불가. 항상 500건 단위로 분할하고 요청 N건 대 응답 M건을 대사한다.

**NICE**
- 가이드와 실제 동작이 다르다. 주문자와 수하인이 달라 일반인증을 요청해도 구매간소화로 응답이 내려온다(2026-08-06). **서면 회신 전까지 이 경로를 신뢰하지 않는다.**
- 제공된 테스트 데이터의 90% 이상이 실패하고 비갱신자(`03`) 시나리오는 테스트가 불가능하다.

**동수 EIBE**
- `hblNo=null`은 버그가 아니라 발송 준비 전 상태다. 같은 주문 `packageList[]`에서 준비된 포장은 값이 있고 후속 포장만 null이다. **최초 조회만 하면 후속 TRA001이 누락된다** — 전 HBL 선발급 또는 Push·재조회 중 하나는 반드시 구현한다.

## 확정 사실

**결정 25건의 전문은 `references/decisions.md`에 있다. 금액·필드·전송 주체를 확정할 때 반드시 그 파일을 읽는다.** 원 정본은 `planning/리스크_질의대장.html`(2026-08-12 통합본).

가장 자주 쓰는 4건만 여기 둔다.
- **신고금액은 동수 ERP의 USD 단가 기준** (2026-08-10). 3사 정합 우선. 규격 문언은 "구매자 최종 결제금액"이므로 **동수 단가와 고객 실결제액 대사표를 주문 단위로 보관**한다.
- **`sellerName`** (2026-08-10) — A 자사몰 = `(주)크로네` Geek 고정 주입 / B 입점채널 = 실제 해외 판매업체명을 동수가 제공. 관세청 `sale_ents_nm`과 동일. **종전 "전건 Null" 폐기.**
- **TRA002 미도입, TRA003 단독 판정 유지** (2026-08-11). 일부 반려 건이 승인으로 출고될 수 있음을 수용된 잔여 리스크로 명시. 제출·응답 건수 일 단위 대사와 `gngMsgCode`(44·99) 사후 탐지로 완화.
- **OTP(`tempAuthNo`)는 `addField`·동수 전달 대상이 아니다** (2026-08-12). Geek DB 보관 후 자이언트로 직접 전송, 자이언트가 HBL 기준 병합. PCCC는 종전대로 `addField` 경유.
