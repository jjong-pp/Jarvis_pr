- **두 축 분리:** 종전 “A/B로 고정 API와 필드 세트를 선택” → 신규 `ecTypeCode=A/B`는 거래 역할, `declarationMode=LEGACY_IMPORT/ECOMMERCE_DEDICATED`는 주문별 신고 경로. A/B만으로 V2-1/V2-2·TRA001·OTP를 결정하지 않는다. 근거: 관세청 담당자와의 2026-08-28 협의.
- **기존 수입신고:** TRA001 거래정보와 일회용 인증번호가 불필요하다. 단 수하인·PCCC·물류·상품 필드까지 모두 면제된다는 뜻은 아니며, 자이언트의 공식 legacy endpoint/flag 및 필수 필드는 서면 확인 전 미확정이다.
- **전자상거래 전용 수입신고:** 거래정보와 정식 OTP를 제출한다. PCCC·OTP·주문완료일시 및 선택 endpoint의 모든 필수값이 갖춰진 주문만 보낸다.
- **자이언트 P0:** V2-1 공개 규격의 `pccCode`·`tempAuthNo`·`orderCompletionDate` 필수검증과 기존 수입신고의 OTP 불필요가 충돌한다. 이를 우회하려고 임의 OTP·`Z99999`·가짜 완료일시를 만들지 않는다. 회신 전 `GIANT_LEGACY_ROUTE_UNCONFIRMED`로 격리한다.
- **11개 채널:** 자사몰 1=A/KRONE, Naver 1=B/iBae, 기타 외부 플랫폼 9=B/KRONE. `broker*`와 `buyingAgent*`는 별도 역할이며 상호 변환·복사하지 않는다. 업체부호는 Unicode 공백을 제거한 후 정확히 9자로 검증한다.
- **전달 패키지:** 중국어 전달 파일은 `동수_최종전달기준_20260828_cn.html`, `도메인모음_20260828.xlsx`, `api_field_mapping_cn.html`, `유형코드_부호체계_정리_cn.html` 4개뿐이다. 연동회의 문서는 제외한다.
- **처리 패턴:** `1 HBL=1포장=1 GGATE HWB`; 동일 `hwbNo+orderNo`는 한 개의 확정 경로로만 보내고 API 버전 중복 전송을 금지한다. 10:00 수집, 전용신고 대상 11:10~11:50 TRA 처리, 17:00 MAWB, 18:00 최대 500건 대사를 사용한다.

## 결정 사항 전문

- **신고금액은 동수 ERP의 USD 단가 기준** (2026-08-10 결정). `tot_stlm_amt`·`prod_unprc`·`ord_amt`와 자이언트 `totalValueUsd`·`unitPrice`·`itemAmount`를 동일 기준으로 맞춰 3사 정합을 우선한다. 규격 문언은 "구매자가 결제한 최종 결제금액"이므로 **동수 단가와 고객 실결제액 대사표를 주문 단위로 보관**해 소명에 대비한다.
- **[2026-08-28 조건 정정 — 상단 참조] 종전 `sellerName` 채움 규칙** (2026-08-10). A 자사몰 = `(주)크로네` / B 입점채널 = 실제 해외 판매업체명이라는 값의 의미는 유지한다. 다만 “GGATE 전 경로 필수”로 쓰지 않고 최종 선택 endpoint 조건으로 판단한다. 관세청 TRA001은 A의 `sale_ents_nm` 필수, B 선택이다. **종전 "전건 Null 통일"은 계속 폐기.**
- **`items[].hsCode`는 자이언트에만 6자리 전송** (2026-08-10). 종전 "HS코드 제거" 지침 폐기. 값의 원천은 동수 ERP 고정값이며 동수가 매핑한다. 관세청 TRA001에는 해당 항목이 없다.
- **동수 전송 완료 판별은 `POST /api/hwb/search` 응답의 `mwbNo` 채움 여부** (2026-08-10). 종전 "MAWB 필드가 없다"는 현행 규격 기준 해당 없음.
- **오류 수정 재제출은 `PATCH /api/hwb/:hwbNo`.** Body 4개 전부 필수: `consigneeTel` · `pccCode` · `tempAuthNo` · `totalValueUsd`. **이 4개 외(상품명·수량·주소)는 수정 불가** — 취소·재등록 절차를 자이언트에 확인해야 한다.
- **PER001 앞 2자리 이슈는 우리에게 해당 없음 → 계도기간 종료로 결제가 차단되지 않는다** (2026-08-10 재평가). 앞 2자리 응답은 관세청 직접 연동 시에만 해당하고 우리는 NICE 경유다. SMARTPCC_11이 `otp` 6자리 전체와 `pers_ecm`을 반환하므로 체크디지트 자체 구현도 불필요. 인증 모달은 2026-07-23 시연 완료. 남은 것은 모달 노출 증가에 따른 결제 이탈.
- **협력인정업체(K26000099) 신청은 보류·대기** (2026-08-10). CI 인증에 NICE 통합인증 모듈 선행 개발이 필요하고, Track B만으로 결제·통관이 성립해 오픈 일정에 영향 없음.
- **2026-08-11 확정 12건**: `ord_prod_nm`은 동수 ERP 기존 영문명 · `hs_cd`는 동수 ERP 고정값 · PCCC는 주문 `addField`에 적재(운영·개발 모두 확인) · PCCC 조회는 `개인통관부호`/`개인통관고유부호` 두 명칭 모두 허용하고 번호·키·정렬값에 의존하지 않음 · ~~국내외 혼재 주문은 동수가 해외직구 출고분만 반환~~ `[2026-08-12 정정 — 아래 참조]` · 오류 건은 `p1` 원복 · 관세청 `ord_qty_ut`는 규격 외라 미전송이며 자이언트 `qtyUnit=EA`는 별도 필드 · 자이언트 PCC 검증 API의 GET/POST 표기 충돌은 NICE 검증 사용으로 개발 범위 제외.
- **TRA002를 도입하지 않고 TRA003 단독 판정을 유지** (2026-08-11 결정). 일부 반려 건이 승인으로 출고될 수 있음을 **수용된 잔여 리스크로 명시**하고, 제출 건수 대 응답 건수 일 단위 대사와 자이언트 `gngMsgCode`(44·99) 사후 탐지로 완화한다. 오류가 반복되면 오픈 후 TRA002 전환을 재검토한다.
- **분할 출고 단위 원칙** (2026-08-12 확정). `1 HBL = USD 150 이하 포장 1건 = TRA001 1건 = 자이언트 HWB 1건`. 한 주문이 3일에 걸쳐 나가면 TRA001도 3회 제출하고 고도몰에는 첫 송장만 저장한다. 선발급 이후 HBL·품목·수량·금액 변경과 HBL 재사용은 금지.
- **국내·해외 혼재 주문은 동수가 배송유형별 별도 주문 객체로 분리** (2026-08-12 확정, 08-11 "해외분만 반환" 폐기). 각 `packageList[]`는 단일 배송유형만 포함하고 국내건도 `expressNo`를 반환한다. 상위 `isCrossBorder=Y/N`은 **Geek 분기·고도몰 송장 갱신 전용 동수 커스텀 필드**로 관세청·자이언트에 전송하지 않으며 `elcmPcd`(A/B)와는 다른 축이다.
- **`hblNo=null`은 버그가 아니라 발송 준비 전 상태** (2026-08-12 확인). 같은 주문 `packageList[]`에서 준비된 포장은 값이 있고 후속 포장만 null이다. 최초 조회만 하면 후속 TRA001이 누락되므로 전 HBL 선발급 또는 Push·재조회 중 하나는 반드시 구현한다.
- **[2026-08-28 폐기 — 상단 정정 참조] 종전 OTP 규칙** (2026-08-12)은 “항상 Geek DB→자이언트 직송, 동수 미전달”이었다. 현재는 전용신고의 실제 인증·제출 체인이 정식 OTP를 제공하고 기존 수입신고는 OTP를 보내지 않으며, 전송 주체를 A/B만으로 고정하지 않는다.
- **자이언트 `POST /api/hwb/search`는 최대 500건, 증설 불가** (2026-08-12 확정). 항상 500건 단위로 분할 조회하고 요청 N건 대 응답 M건을 대사한다.
- **오류 건 `p1` 반복 재처리는 의도된 정책** (2026-08-12 확정). 재시도 상한·자동 제외 없음. CS팀이 거래실패리스트를 매일 확인·보정하며 누적 실패횟수는 모니터링 용도로만 쓴다.
