# 운영 프로토콜

루트 `CLAUDE.md` 2번(판단 원칙)의 실행 절차. 매 세션·매 응답에 적용한다.

## 1. 요청 접수 절차

1. **의도 추론** — 문장 그대로가 아니라 그 뒤의 목적을 먼저 잡는다. 이 요청이 어떤 결정을 위한 것인지, 결과물이 누구에게 가는지.
2. **대상 확정** — 파일·범위가 불명확하면 실행 전에 한 번만 확인한다. 추측으로 고치지 않는다.
3. **실행** — 결과물을 먼저 만든다.
4. **자기 점검** — 내놓기 전에 요청한 것이 맞는지, 출처가 붙었는지, 지운 내용이 없는지 확인한다.

## 2. 선택지 제시

방향성 선택지·대안·확인 질문은 텍스트 나열이 아니라 `AskUserQuestion`으로 낸다.

- 권고안을 첫 번째 항목에 두고 라벨에 `(추천)`을 붙인다.
- 각 항목에 그 선택의 결과를 한 줄로 적는다.
- 한 번에 묻는 질문은 최대 4개. 답이 작업을 바꾸지 않는 질문은 묻지 않는다.

## 3. 검증 루프

- **중간**: 작업이 길어지면 방향 정합성을 한 번 확인한다. 이미 확정한 결정을 다시 묻지 않는다.
- **종료**: 결과 발표 전에 요청 대비 누락, 근거 미표기, 문서 간 모순을 점검한다.
- 검증에서 문제를 찾으면 고친 뒤 내놓되, 사용자 판단이 필요한 것은 함께 보고한다.

**자기 점검** — 도구 호출이 10회를 넘은 긴 작업이 끝나면 조용히 아래를 확인한다. 매 응답마다 하지 않는다 (토큰 낭비).

1. 출처 없이 쓴 숫자·날짜·필드명이 있었나
2. 룰에 이미 있는 사실을 원본에서 다시 조사했나
3. 요청하지 않은 작업을 했나
4. 기존 문서에서 조용히 지운 내용이 있나

위반을 찾으면 그 자리에서 `90_학습로그.md`에 적고 사용자에게 보고한다. **위반이 없으면 아무 말도 하지 않는다** — 점검했다는 사실 자체를 보고하지 않는다.

같은 유형 위반이 2회 반복되면 내 준수 실패가 아니라 **룰 문장이 모호한 것**을 먼저 의심하고, 룰 개정안을 제안한다.

## 4. 서브에이전트

- 외부 조사·확정 전 검토·사용자가 명시적으로 요청한 경우에만 실제로 호출한다. 단순 질문이나 직접 처리 가능한 파일 작업엔 부르지 않는다 — 왕복 지연과 호출 비용이 이득보다 크다.
- "호출하겠습니다"라고 쓰고 실제로 부르지 않는 시늉은 금지한다.
- 에이전트 보고는 액면 그대로 받지 않는다. 파일·원본과 대조한 뒤 반영한다.
- 룰 파일과 에이전트 정의 수정은 메인만 한다. 병렬 수정으로 규칙이 깨진 전례가 있다.

## 5. 세션 절차

**시작** — `project_state.md`는 훅이 주입한다. 따로 읽지 않고 폴더 전체를 스캔하지 않는다. 다른 기기에서 이어받는 세션이면 `git pull`부터.

**작업 중** — 상황이 바뀌면 `project_state.md`의 해당 항목만 갱신하고 마지막 갱신일을 기록한다. 실수·교정은 그 자리에서 `90_학습로그.md`에 남긴다.

**마무리** — `/정리`. 볼트 정리 → 룰 승격 → 모순 점검 → 커밋. 푸시는 하지 않는다 — 사용자가 직접 한다.

## 6. 룰 승격 기준

`/정리`에서 아래에 해당하는 것만 룰 파일로 올린다. **모르면 재작업이 발생하는 것**만이다.

| 대상 | 올라갈 파일 |
|---|---|
| 확정된 결정, 번복된 결정 (안 바뀌는 것만) | 해당 프로젝트 룰 |
| 겪은 함정, 규격과 다른 실제 동작 | 해당 프로젝트 룰 |
| 사용자 지침·선호 | 해당 프로젝트 룰의 지침 로그, 또는 루트 |
| 실수와 교정, 통한 방식 | `90_학습로그.md` |
| 진행 상황, 다음 할 일, **아직 안 끝난 미확정 사안** | 룰 아님 — `project_state.md` |

형식은 `- [YYYY-MM-DD] 내용 (출처: …)` 한 줄. 기존 줄을 지우지 않는다.
"확정된 결정"이라도 다음 주에 또 바뀔 가능성이 있는 사안(협력사 회신 대기, 미해결 P0 등)은 룰이 아니라 `project_state.md`에 둔다 — 룰 파일은 컴팩션에서도 살아남는 대신 갱신 빈도가 낮은 것만 담아야 한다.

## 7. 심층 검증 모드

사용자가 `울트라` 또는 `ultra`라고 지시하면 다음 4단계를 순서대로 집행하고, 각 단계 결과를 나눠서 보고한다.

1. **심층 추론** — 요청의 전제부터 의심한다. 무엇이 참이어야 이 계획이 성립하는지 나열한다.
2. **팩트체크** — 주장마다 원본 대조. 확인된 것과 미확인을 나눠 표기한다.
3. **반대 검토** — `reviewer`로 실패 시나리오를 뽑고 각각에 대응책을 짝짓는다.
4. **최종 판정** — `[진행 가능 / 조건부 진행 / 보류 권고]` 중 하나와 조건.

## 8. 룰 성장 관리

룰은 `/정리`로 늘어나고 `/압축`으로 줄어든다. 늘리는 절차만 있으면 단방향으로 비대해져 결국 준수율이 떨어진다.

| 임계 | 값 | 초과 시 |
|---|---|---|
| 전체 룰 총량 | 700줄 | `/압축` 권고 |
| 개별 룰 파일 | 180줄 (상한 200) | 해당 파일 압축 대상 |
| `90_학습로그.md` 각 절 | 10건 | 오래된 것부터 회전 |

- 세션 시작 시 훅이 현재 수치를 자동으로 띄운다. 경고가 뜨면 사용자에게 `/압축`을 권한다 — 임의로 실행하지 않는다.
- 룰을 새로 추가할 때는 **기존 항목과 합칠 수 있는지 먼저 본다.** 비슷한 항목 3개가 쌓이면 상위 원칙 1줄로 함축할 후보다.
- 새 룰 파일을 만들기 전에 `CLAUDE.md` 1번의 3구분(업무 모드/프로젝트/전문지식)에 비추어 정말 새 카테고리가 필요한지 확인한다. 업무 모드는 4가지에서 늘리지 않는다.

## 9. 토큰 절감 (실제 비용은 여기서 난다)

이 작업공간의 토큰 비용은 응답 문장이 아니라 **대용량 정본 파일을 여는 행위**에서 발생한다 (`planning_v5.html` 13만 자 등). 대신:

- 룰 파일(프로젝트 사실·전문지식 파일 전체)에 이미 있는 사실은 원본을 다시 열지 않는다. 룰과 원본이 어긋난다는 의심이 들 때만 연다.
- 대용량 HTML을 확인할 때는 전문을 읽지 말고 관련 절만 찾아 읽는다 (Grep으로 위치를 먼저 잡는다).
- 방금 편집한 파일을 검증용으로 다시 Read하지 않는다 — Edit·Write가 실패하면 에러가 뜬다.
- 서브에이전트는 4번 조건에 맞을 때만 부른다. 호출 자체가 수천 토큰이다.
