# AI 하네스 엔지니어링 — Part 1. 모델이 똑똑해져도 일 못하는 이유

---

## 1. 똑똑한 AI인데, 왜 아직도 일을 하나하나 지시해야 할까요?

저는 약 반 년간 AI 에이전트를 실무에 깊게 붙여 써왔습니다. 코드 작성, 리서치, 기획, 메일 작성, 프로젝트 관리까지 — 쓸 수 있는 곳이라면 어디든 투입했습니다.

도구는 점점 좋아졌습니다. **Gemini Ultra**의 컨텍스트 윈도우는 200만 토큰을 넘기고, **Claude**는 정교한 코드를 뽑아내는 능력이 눈에 띄게 올라갔습니다.

그런데 이상한 점이 하나 있었습니다.

모델이 더 똑똑해질수록, 제가 해야 하는 일은 전혀 줄어들지 않았습니다.

에이전트에게 일을 시키려면 제가 먼저 어떤 스킬을 써야 하는지를 판단해야 했습니다. 코드를 짜달라고 하면 `@software-engineering`을 붙여야 하고, 조사를 시키려면 `@deep-research`를 호출해야 하고, 검토를 부탁하려면 `@qa-review`를 명시해야 했습니다.

스킬이 14개까지 늘어나자, 저는 AI를 쓰기 위해 **AI의 내부 구조를 암기**하고 있었습니다. 이건 분명히 뭔가 잘못된 방향이었습니다.

---

## 2. 현장에서 터진 3가지 사건: 진짜 병목은 어디에 있었을까요?

결정적인 문제는 모델의 지능이 아닌 전혀 다른 곳에서 터졌습니다.

#### 사건 1. 서브에이전트 비동기 수정으로 인한 '설정 파일 부패'
복잡한 작업을 병렬로 처리하기 위해 서브에이전트 3개를 동시에 띄웠습니다. 

각 에이전트가 같은 글로벌 규칙 파일(`master_global_rules.md`)을 동시 다발적으로 수정했는데, 작업이 끝나고 보니 파일이 엉망이 되어 있었습니다.

```diff
- 규칙 19: 오케스트레이션 엔진을 2개로 통합하여 운영한다.
+ 규칙 20: 오케스트레이션 엔진은 3개 엔진(Gemini, Claude, GPT)을 각각 독립 나열하여 운영한다.
```

규칙 19번과 20번이 서로 충돌하는 모순이 발생했고, 20개의 규칙이 우선순위 없이 나열되어 있어서 에이전트 스스로도 어떤 규칙을 따라야 하는지 판단할 수 없는 상태가 되었습니다. 결국 파일 전체를 지우고 처음부터 다시 쓰는 **Clean Rewrite**를 해야 했습니다.

#### 사건 2. 문서 통합 시 발생한 '핵심 내용 실종'
두 개의 운영 가이드 문서를 하나로 합치는 작업을 시켰습니다. 

깔끔하게 통합된 줄 알았는데, 원본에 있던 작업 라우팅 의사결정 트리, 일일 운영 타임라인, 산출물 가이드, 비용 관리 상세 등 **가장 중요한 실무 지침 5가지가 통째로 삭제**되어 있었습니다. 목차만 그럴듯하고 내용은 비어있는 매뉴얼이 만들어진 것입니다.

#### 사건 3. 껍데기만 남은 16줄짜리 스킬 파일
새로 만든 스킬 파일 3개의 내용을 열어보니 전부 16줄이었습니다. 

4줄짜리 추상적인 규칙만 달랑 적혀 있고, 구체적인 절차도, 예시도, 금지사항도 없었습니다. 이걸 로드해봤자 에이전트가 얻는 가이드는 **"잘 해라"** 수준에 불과했습니다.

> **"모델은 이미 충분히 똑똑했습니다. 모델을 제어하는 구조가 부실했을 뿐입니다."**

---

## 3. 하네스 엔지니어링: 야생마에게 고삐와 안장을 씌우다

저는 이 문제의 본질을 **오케스트레이션(Orchestration)의 부재**라고 정의했습니다.

소프트웨어 분야에는 **테스트 하네스(Test Harness)**라는 개념이 있습니다. 테스트 대상을 제어된 환경에 집어넣고, 입력을 주입하며, 출력을 검증하고, 이상이 생기면 안전하게 멈추게 하는 **제어 구조물**을 뜻합니다.

아무리 뛰어난 **야생마(LLM)**라도 고삐와 안장(**Harness**)이 없으면 기수를 태우고 목적지까지 달릴 수 없습니다. 

저는 이 개념을 에이전트 운영에 가져와 **하네스 엔지니어링(Harness Engineering)**이라 이름 붙였습니다.

$$\text{Agent System} = \text{Model Intelligence (지능)} + \text{Harness Control (구조)}$$

핵심 철학은 간단합니다. **"모델이 지능을 제공하고, 하네스가 구조를 제공한다."** 모델에게 무작정 더 똑똑해지라고 요구하는 대신, 가진 지능을 올바른 방향으로 쓰도록 **구조적 제어망**을 씌우는 것입니다.

---

## 4. 매번 풀가동할 필요가 있을까요? — 3단계 게이팅(Gating) 시스템

하네스를 설계하면서 부딪힌 첫 번째 장벽은 **토큰 비용과 응답 지연**이었습니다.

"모든 대화 턴에서 의도를 분석하고, 스킬을 매칭하며, 서브에이전트를 띄운다"는 원칙은 좋지만, `"지금 진행 상황이 어때?"` 같은 단순 질문에도 전체 파이프라인을 돌리면 토큰 낭비가 심각해집니다.

고속도로 톨게이트의 하이패스 차선처럼, 작업의 무겁기에 따라 차로를 자동으로 안내해 주는 **3단계 게이팅(Three-Level Gating)** 시스템을 고안했습니다.

사용자 메시지가 들어오면 다음 4가지 시그널을 즉시 평가합니다.

1. **Multi-file Change**: 수정해야 할 파일이 2개 이상인가?
2. **Architecture Impact**: 시스템 구조를 바꾸는 작업인가?
3. **Cross Verification**: 여러 관점의 교차 검증이 필요한가?
4. **Explicit Deep Task**: 사용자가 심층 작업을 명시했는가?

| 게이팅 레벨 | 진입 조건 (Signal) | 작동 방식 (Execution) | 토큰 오버헤드 |
| :--- | :--- | :--- | :---: |
| **Level 0 (경량 직답)** | 시그널 **0개** (단순 질의) | 하네스 로딩 우회, 즉시 응답 | **0%** |
| **Level 1 (단일 스킬)** | 시그널 **1개** (단일 기능) | 필요한 스킬 1개 로드 후 실행 | **10~20%** |
| **Level 2 (풀 오케스트레이션)** | 시그널 **2개 이상** (복합 모듈) | 서브에이전트 동적 생성 및 병렬 투입 | **4~5배** |

실제 일상 대화의 70~80%는 **Level 0**이나 **Level 1**에서 처리되므로, 시스템 전체의 비용과 속도 균형을 완벽하게 맞출 수 있습니다.

## 5. 불확실할 땐 되물어라 — 확신도 기반 에스컬레이션

게이팅 시스템의 위험 요소는 바로 **오판(Misjudgment)**입니다.

단순 작업을 Level 2로 올려 토큰을 쏟아붓거나, 복잡한 시스템 변경을 Level 0으로 처리하여 누더기 코드를 만드는 오판을 막기 위해 **확신도 기반 에스컬레이션(Confidence-Based Escalation)** 패턴을 적용했습니다.

에이전트가 답변을 내기 전, 스스로 다음 3가지 질문으로 **자가 진단**을 수행합니다.

```text
[Self-Confidence Check]
1. Goal: 최종 작업 목표를 한 문장으로 명확히 정의할 수 있는가?
2. Target: 수정 또는 참조 대상 파일/위치를 특정할 수 있는가?
3. Skill: 매칭된 스킬과 실행 지침이 명확한가?
```

* **Yes가 3개**: 지체 없이 자동 실행합니다.
* **Yes가 2개**: `"이러한 방향으로 작업을 진행하겠습니다."`라고 사용자에게 명시한 뒤 실행합니다.
* **Yes가 1개 이하**: 섣불리 실행하지 않고, **사용자에게 질문을 던져 의도를 재확인**합니다.

이 작은 안전장치 하나로 에이전트가 불확실한 상태에서 임의로 코드를 엎어버리는 사고를 구조적으로 차단했습니다.

## 6. 규칙이 충돌할 땐 누가 이길까요? — 4-Tier 룰 계층화

설정 파일이 썩는 문제를 해결하기 위해 마이크로서비스의 **우선순위 기반 정책 엔진(Priority-Based Policy Engine)** 사상을 도입했습니다. 20개의 규칙을 4개의 계층(Tier)으로 구분하고, 상위 계층이 하위 계층을 자동으로 오버라이드하도록 설계했습니다.

| Tier | 계층명 | 주요 역할 | 우선순위 (Precedence) | 충돌 시 동작 규칙 |
| :--- | :--- | :--- | :---: | :--- |
| **Tier 1** | **자율 하네스** | 게이팅, 의도 파싱, 자가 교정 | **P0 (최우선)** | 하위 Tier의 모든 규칙을 오버라이드함 |
| **Tier 2** | **아키텍처** | 엔진 분담, 세션 및 저장소 구조 | **P1** | 하네스 제어망 범위 내에서 아키텍처 준수 |
| **Tier 3** | **보안 및 데이터** | API Key 보호, 백업, 로그 관리 | **P2** | 실행 과정에서의 데이터 안전선 확보 |
| **Tier 4** | **규격 & 포맷** | 타임스탬프, 마크다운 톤앤매너 | **P3 (최하위)** | 상위 제약이 없을 때만 스타일 적용 |

예를 들어 Tier 4의 `"모든 출력에 타임스탬프를 명시하라"`와 Tier 1의 `"Level 0에서는 하네스 오버헤드를 우회하라"`가 충돌하면, **Tier 1이 승리**하여 불필요한 로그 생성을 생략합니다.

## 7. 정리하며: 다음 편에서는 무엇을 다룰까요?

모델의 지능은 이미 훌륭합니다. 문제는 그 지능을 제어하는 **구조(Harness)**에 있었습니다.

* **3단계 게이팅**으로 비용과 속도의 균형을 잡았습니다.
* **확신도 에스컬레이션**으로 모호한 실행을 차단했습니다.
* **4-Tier 계층화**로 규칙 충돌을 자동 해소했습니다.

그렇다면 사용자 메시지가 입력된 바로 그 순간, **하네스의 내부 엔진은 어떻게 의도를 파싱하고 서브에이전트들을 조종할까요?**

다음 글 **Part 2. 의도를 읽는 에이전트 만들기**에서는 의도 파서의 JSON 스키마, 14개 스킬 동적 매칭 알고리즘, 그리고 서브에이전트들이 협력하는 실전 시뮬레이션을 낱낱이 파헤쳐 보겠습니다.
