# AI 하네스 엔지니어링 — Part 2. 의도를 읽는 에이전트 만들기

---

Part 1에서는 3단계 게이팅과 4-Tier 룰 계층화라는 하네스의 뼈대를 세웠습니다. 이번 글에서는 하네스의 진짜 핵심 심장인 **자율 의도 오케스트레이션(Autonomous Intent Orchestration)** 엔진이 내부에서 어떻게 돌아가는지 그 내부 메커니즘을 열어보겠습니다.

---

## 1. 왜 에이전트는 새 창을 열 때마다 어제의 일을 잊어버릴까요? — Phase 0: 세션 초기화

LLM 기반 에이전트와 일할 때 가장 답답한 순간은 바로 **지독한 기억 상실증**입니다. 

어제 하루 종일 코드 컨벤션을 맞추고 에러를 수정해 두었는데, 오늘 새 창을 열면 다시 백지상태가 되어 "우리 프로젝트는 말이죠..."라며 구구절절 처음부터 설명해야 했습니다.

이 문제를 해결하기 위해, 에이전트가 출근하자마자 업무 일지와 오답 노트를 펴보듯 **세션이 시작되는 순간 과거의 기억을 자동으로 복원하는 Phase 0 (`state-sync`)** 루틴을 만들었습니다.

```text
[Phase 0: Memory Synchronization Engine]
 ├─ project_state.md   : 현재 마일스톤 및 진행 상황
 ├─ error_patterns.md  : 자주 발생하는 에러 패턴 및 방지책
 ├─ success_patterns.md: 검증된 모듈 아키텍처 및 디자인 패턴
 └─ error_journal.md   : 최근 5건의 실무 오답 노트 및 사용자 교정 사항
```

에이전트는 질문을 받기 전 위 4개 마크다운 파일을 먼저 읽어들입니다. 어제 작성한 `"A API 대신 B API를 사용하라"`는 교정 사항이 `error_journal.md`에 기록되어 있다면, 오늘 새 세션에서는 묻지 않고도 B API를 사용하는 구조입니다.

## 2. 키워드 몇 개로 사람의 진짜 의도를 읽을 수 있을까요? — Phase 1: 의미적 의도 파서

초기에는 단순 키워드 매칭을 사용했습니다. `'메일'`이 들어가면 이메일 스킬을, `'버그'`가 들어가면 디버깅 스킬을 켜는 방식이었습니다. 하지만 인간의 실제 대화는 훨씬 복잡합니다.

예를 들어 제가 `"이 API 응답 구조가 좀 이상한 것 같은데"`라고 메시지를 남겼다고 해보겠습니다. 이 문장에는 '버그', '수정', '코드' 같은 명시적 키워드가 하나도 없습니다. 키워드 매칭 방식이라면 에이전트는 어리둥절하며 엉뚱한 답변을 냈을 것입니다.

이를 극복하기 위해 파서가 메시지의 행간을 읽어 **4대 핵심 요소**를 정형 데이터로 추출하도록 프롬프트를 설계했습니다.

```json
{
  "goal": "API 응답 구조 이상 원인 분석 및 수정",
  "target_files": ["src/api/response.py", "src/models/schema.py"],
  "constraints": ["기존 v1 API 클라이언트와의 호환성 유지"],
  "urgency": "HIGH",
  "gating_evaluation": {
    "multi_file_change": true,
    "architecture_impact": false,
    "cross_verification_needed": true,
    "explicit_deep_task": false
  },
  "determined_level": "LEVEL_2"
}
```

키워드가 없어도 **"응답이 이상하다"**는 불평에서 **"코드를 분석하고 수정해야 한다"**는 목표(Goal)를 도출하고, 이에 따른 **게이팅 레벨(LEVEL_2)**까지 스스로 판정해 내는 것입니다.

---

## 3. 14개 도구 상자 중 최적의 무기를 찾는 방법 — Phase 2: 동적 스킬 매칭

의도를 파악했다면 이제 어떤 도구를 꺼내 들지 결정해야 합니다. 제 하네스에는 현재 14개의 스킬이 정의되어 있습니다.

에이전트는 하드코딩된 규칙 테이블을 뒤지는 것이 아니라, 추출된 4대 요소를 바탕으로 각 스킬 폴더의 `SKILL.md` 명세를 읽고 **의미적 부합도**를 추론합니다.

* **0개 매칭**: 적합한 스킬이 없으면 억지로 스킬을 켜지 않고 일반 대화 모드로 전환합니다.
* **1개 매칭**: 해당 스킬의 실행 가이드를 즉시 로드하여 작업을 수행합니다.
* **2개 이상 매칭**: 예를 들어 `"데이터를 분석해서 결과를 보고서 메일로 보내달라"`는 요청에는 `data-analytics`와 `email-writer` 스킬이 동시에 선택됩니다. 에이전트는 이 두 스킬의 **우선순위 실행 파이프라인**을 스스로 구축합니다.

---

## 4. 똑똑한 클론 3명보다 '가면'을 쓴 3명이 모이면 무슨 일이 벌어질까요? — 동적 페르소나 생성

게이팅에서 **Level 2(풀 오케스트레이션)** 판정이 내려지면, 메인 에이전트는 혼자 일하지 않고 서브에이전트들을 생성합니다.

영화 촬영장에서 감독(메인 에이전트)이 무술 감독, 조명 감독, 연출 감독(서브에이전트)에게 각자의 전문 역할을 부여하는 것과 같습니다. 메인 에이전트는 `define_subagent` 도구를 사용해 작업 직전에 뾰족한 **전문 페르소나**를 즉석에서 깎아냅니다.

```text
[Dynamic Persona Definition]
 ├─ SubAgent A: "너는 방어적 프로그래밍에 미친 보안 감사관이야. SQLi와 토큰 유출을 집중 감시해."
 ├─ SubAgent B: "너는 레거시 코드 호환성에 집착하는 리팩토링 전문가야."
 └─ SubAgent C: "너는 엣지 케이스를 사냥하는 TDD 테스트 엔지니어야."
```

이렇게 부여된 서브에이전트들을 `invoke_subagent` 배열에 담아 한 번에 병렬로 투입합니다. 밋밋한 클론 3명이 모였을 때보다 결과물의 정교함과 밀도가 차원이 다르게 올라갑니다.

## 5. 실수했을 때 무한 루프를 막는 자가 교정 피드백 루프

에이전트도 실수를 합니다. 스크립트 실행 중 에러가 나거나 엉뚱한 코드를 짜기도 합니다. 무제한 재시도로 토큰을 다 태워버리는 현상을 막기 위해 **2단계 자가 교정 루프**를 구축했습니다.

1. **1차 실패 (Automated Fallback)**: 즉시 대체 경로를 시도합니다. 예를 들어 외부 API 조회가 실패하면 멍하니 멈추지 않고 즉시 Web Search 모듈로 우회합니다.
2. **2차 실패 또는 사용자 교정**: 즉시 실행을 멈추고 현 상태와 원인을 요약한 브리핑 리포트를 띄운 채 지시를 기다립니다.

> **"실패는 허공으로 날려버릴 스팸 데이터가 아니라, 다음 세션을 위한 가장 귀중한 자산입니다."**

모든 오류와 사용자의 교정 피드백은 발생 즉시 `error_journal.md`에 단일 라인으로 기록되며, 이 기록은 다음 날 Phase 0에서 다시 로드되어 **실수를 먹고 성장하는 선순환 구조**를 완성합니다.

## 6. 실전 시뮬레이션: 시스템은 실제로 어떻게 움직일까요?

### 🔹 Level 0 시나리오: 단순 현황 질의
> **USER**: `"지금 진행 중인 프로젝트 상태가 어때?"`

```text
[Trace Log: Level 0]
 ├─ [Phase 1 Intent Parser] Goal: 프로젝트 현황 브리핑 / Target: project_state.md / Gating: LEVEL_0
 ├─ [Phase 2 Skill Match] Matched: None (단순 파일 읽기)
 └─ [Execution] view_file("project_state.md") ➔ 요약 답변 작성 후 즉시 종료 (오버헤드 0%)
```

---

### 🔹 Level 1 시나리오: 단일 스킬 실행
> **USER**: `"내일 거래처 미팅 확정 이메일 초안 작성해 줘."`

```text
[Trace Log: Level 1]
 ├─ [Phase 1 Intent Parser] Goal: 비즈니스 이메일 작성 / Target: 미팅 일정 / Gating: LEVEL_1
 ├─ [Phase 2 Skill Match] Matched: `email-writer` (사용자 어투 모방)
 └─ [Execution] view_file("skills/email-writer/SKILL.md") 로드 ➔ 톤앤매너 적용 ➔ 마크다운 초안 생성
```

---

### 🔹 Level 2 시나리오: 다중 서브에이전트 병렬 오케스트레이션
> **USER**: `"새 결제 모듈을 설계하고 구현해 줘. 기존 API와 호환되어야 하고, 보안 검토랑 테스트 코드도 필수야."`

```text
[Trace Log: Level 2 Multi-Agent Discussion]

[Main Orchestrator] Level 2 판정 ➔ define_subagent로 페르소나 3종 동적 생성
 ├─ SubAgent A: [Backend_Dev] (기존 API 호환 모듈 작성)
 ├─ SubAgent B: [Security_Auditor] (Zero-Trust 보안 검증)
 └─ SubAgent C: [Test_Engineer] (TDD 테스트 스위트 작성)

[Step 1] Backend_Dev ➔ 결제 모듈 초안 작성 (`src/payment.py`)
[Step 2] Security_Auditor ➔ 초안 검토 중 동적 SQL 쿼리 우려 감지 (REJECT & 피드백 전달)
[Step 3] Backend_Dev ➔ ORM 바인딩 방식으로 코드 수정 및 Diff 업데이트 (PASS)
[Step 4] Test_Engineer ➔ 수정된 모듈 대상 엣지 케이스 단위 테스트 작성 (`tests/test_payment.py`)
[Step 5] Main Orchestrator ➔ 최종 검증 완료된 코드 및 테스트 결과 보고서 제시
```

## 7. 정리하며: 거창해 보이는 이 시스템, 정말 실전에서 쓸만할까요?

Part 2에서는 의도를 읽고, 스킬을 찾아내며, 서브에이전트들이 서로 검증하는 내부 엔진을 다루었습니다.

그렇다면 남은 진짜 질문은 이것입니다. 

* **이 시스템의 실제 토큰 비용은 얼마나 들까요?**
* **Gemini에 하네스를 얹으면 정말 Claude 수준의 정교함이 나올까요?**
* **실제로 운용하면서 터졌던 3가지 기술적 구멍과 땜질 해결책은 무엇이었을까요?**
