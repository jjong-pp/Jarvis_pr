Stage 1. 结账环节 PER001 个人通关固有符号预先有效性验证 顾客结账瞬间 (实时)

详细发送及处理逻辑 (Geek 自营商城实务):

  • 背景及目的: 在自营商城结账阶段预先验证个人通关固有符号，拦截因错误符号或姓名不符导致的通关被拒及延迟。
  • 处理流程:
    1. 自营商城顾客在结账页面输入收件人姓名(cnsi_nm)、个人通关固有符号(cnsi_pers_ecm)、电话号码(cnsi_telno)。
    2. 自营商城(Geek)后端实时同步调用海关 PER001 API，验证姓名-符号-电话号码三者一致性。
    3. 验证成功时: 将海关响应的 6位认证号码(su_crtf_no)保存至自营商城 DB 订单表，并完成结账批准 (订单状态 p1)。
    4. 验证失败时: 立即拦截结账批准，并在页面弹出 "您输入的通关符号与姓名不符" 警告提示。

Stage 2. 09:00 东数 EIBE ERP 订单采集及订单状态变更 g1(商品准备中) 每天 09:00 批处理

详细发送及处理逻辑 (Geek - 东数 EIBE ERP 联动):

  • 背景及目的: 东数 EIBE ERP 采集订单以备当日海外发货，并锁定个人中心取消功能，保障物流作业安全。
  • 处理流程:
    1. 每天 09:00 东数 EIBE ERP 调用自营商城 Open API 批量采集 p1(支付完成) 状态订单。
    2. 自营商城(Geek)收到采集请求后，立即将对应订单状态更新为 g1(商品准备中)。
    3. 进入 g1 状态后，个人中心 "取消/退款" 按钮自动隐藏，禁止顾客直接取消。

详细发送及处理逻辑 (自营商城专用 TRA001 构建):

  • 处理流程:
    1. 11:10采集EIBE ERP的HBL及TRA数据: 自营商城(Geek)调用东数 EIBE ERP 的 getTRA001OrderInfo（仅限海外 TRA 信息），取得预分配 hbl_no、预估重量、HBL申报货值候选、HS Code、渠道提交配置(kcsSubmitterCode/Name、submissionProfileKey)等数据（商品序号 prod_srno 已改为 Geek 自行编号，不再向东数索取）。11:50前未取得全部HBL或明确TRA结果的订单转为MANUAL_CLEARANCE_REQUIRED。[2026-08-26 确定] KCS tot_stlm_amt 与 GIANT totalValueUsd 统一使用东数 ERP 的 USD 采购金额；原“须取客户最终支付金额、不得使用东数采购价”指示废止。国内及海外运单号和 isCrossBorder=Y/N由现有serachOrderInfo返回，不得混用两者职责。
    2. 组合自营商城 A 类型代码、企业代码及 URL:
    - elcm_pcd (销售类型代码): 按2026-08-24确认值注入 'A' (直接销售)
    - elcm_ents_sgn / elcm_ents_nm (提交方): K26000099 / (株)KRONE
    - puch_vcex_bsmn_sgn / puch_vcex_bsmn_nm (代购企业): A类型禁止发送，保持Null
    - sale_ents_sgn=K26000099、sale_ents_nm=(株)KRONE；GIANT使用sellerCode=K26000099、sellerName=(株)KRONE、broker*=K26000099/(株)KRONE，并禁止发送buyingAgent*
    - prod_sale_pge_url (商品 URL): 使用订单商品/商品DB中的实际详情页URL，不以商城首页统一代替
    3. 100条分块发送: 按海关 REST API 规范，按 100条分块(Chunk)提交 TRA001 预先申报。

状态流转 — p1支付完成 → 东数采集后g1商品准备中 → 11:10开始HBL采集 → 11:50前仅明确正常订单进入g5候选并更新运单号。错误、缺失、延迟、结果未确定或删除失败的订单进入MANUAL_CLEARANCE_REQUIRED，禁止自动TRA及自动出库；记录人工申报编号和批准人后方可人工解除。

6. [2026-08-25 确定] Geek/东数分开写入GIANT

Geek通过POST /api/hwb/bulk-sync/clearance写入通关·订购人·收件人信息；东数DS Logistics于17:00~18:00通过POST /api/hwb/bulk-sync/logistics写入物流·商品数据，GIANT按hwbNo + orderNo合并。先到侧保存为pending，双方到齐后返回merged。

Geek发送项 — hwbNo · orderNo · pccCode · tempAuthNo · orderer* · consignee* · orderCompletionDate。不发送东数物流·商品字段。

东数发送项 — 物流、包装、发货人、金额、渠道ecTypeCode、broker*、条件性buyingAgent*、orderSiteUrl及items[]。不发送PCCC、OTP、订购人或收件人字段。

※ A：broker*与sellerCode必填，禁止发送buyingAgent*；B：broker*与buyingAgent*必填，sellerCode选填。sellerName始终必填。

7. 已确认事项 (无需再讨论)

  • 国内/跨境混合订单 — [2026-08-25 更新] isCrossBorder与elcmPcd是不同维度。跨境订单按渠道分为自营商城A和外部平台B；不得把全部isCrossBorder=Y统一写成B。Geek仅提交HBL已准备的跨境包裹。
  • 套装商品 — 以套装内单品信息提供，而非套装单位 (2026-08-06)
  • 跨日拆单发货 — 1个HBL对应1次TRA001；3天分3次发货则提交3次。Godomall只保存第一个运单号，但Geek内部必须按分拆包裹管理提交状态。若不增加Geek批处理，东数必须首次查询时预分配全部HBL，或在后续HBL生成时Push (2026-08-12)
  • 快照一致性 — 14个属性中仅实测重量(weight)在11:10预估快照与17:00实测快照之间允许变化，其余字段须按双方批准规则保持一致
  • 订单删除API — POST /api/openAPI/erp/orderInfo/orderDelete，参数customerOrderNo，单次1件。母订单号可能连带删除全部子订单；如存在国内/海外混合或删除范围未确认，不得自动调用，须转为人工通关及运营保留
  • 个人通关唯一编码(PCCC)与 OTP — Godomall addField中既有 PCCC 字段可用于订单内部核对，但 GIANT 的 PCCC、OTP、订购人及收件人写入由 Geek 负责。
    ※ [2026-08-19 更正] tempAuthNo(OTP) 不进入 addField，也不由东数发送；由 Geek 保存并直送 GIANT。旧“东数 bulk-sync 发送 PCCC/OTP”的指示废止。
