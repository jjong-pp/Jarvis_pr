## 1. 판정

**현재 기획대로 개발하면 첫 주문의 결제 단계에서 멈춥니다.**

2026-08-06 재평가는 "운영 반영 NO-GO"였습니다. 이번 검증은 판정을 한 단계 더 내립니다. 문제는 운영 리스크가 아니라 **개발 착수 자체가 불가능한 스펙 공백**입니다. 이유는 세 가지입니다.

1. PER001 응답이 인증번호 6자리를 준다는 전제가 **일반 경로에서 거짓**입니다. 관세청은 앞 2자리만 줍니다.
2. 그 전제를 우회하는 유일한 경로(협력인정업체 간소화)는 **기획서 어디에도 등장하지 않는 자격 조건**을 요구합니다. `협력인정업체`라는 단어가 planning_v5와 api_field_mapping에 **0회** 나옵니다.
3. 자이언트 HWB 등록은 `pccCode`와 `tempAuthNo`를 **둘 다 필수**로 요구합니다. 따라서 카톡에서 논의된 "그냥 CI 배제하고 주문마다 PCCC 인증만 돌린다"(2안)도 인증번호 확보 문제를 피해가지 못합니다.

즉 지금 기획은 A안·B안 어느 쪽으로 가도 **인증번호 6자리를 어떻게 손에 넣을지가 비어 있습니다.**

## 2. E2E 시뮬레이션 — 어디서 터지는가

planning_v5의 Stage 1~7을 실제 데이터로 흘려봤습니다.

### Stage 1 — 결제 시점 PER001 · **즉시 실패**

기획: `cnsi_nm` + `cnsi_pers_ecm` + `cnsi_telno` 3개를 보내고 `su_crtf_no` 6자리를 받아 결제 완료.

실제 v1.4.1 PER001 요청 스키마:

| 공식 필수 항목 | 기획 반영 |
|---|---|
| `reqt_no` String(18) — yyyyMMddHHmm+일련번호6 | **없음** |
| `reqt_tp` String(2) — 01 일반 / 02 협력인정업체 | **없음** |
| `ordrr_info.ordrr_fnm` String(150) 주문자 성명 | **없음** |
| `cnsi_info.cnsi_fnm` (기획은 `cnsi_nm`으로 표기) | 이름 불일치 |
| `cnsi_info.cnsi_telno` | 있음 |
| **`cnsi_info.dlvrpl_psno` String(5) 배송지 우편번호** | **없음** |
| `cnsi_pers_ecm` (reqt_tp=01일 때 필수) | 있음 |
| `ord_no_icln_tp` String(2) — 주문번호 포함 구분 | **없음** |

요청 자체가 구성되지 않습니다. 필수 5개가 빠져 있습니다.

응답은 더 심각합니다. v1.4.1 [붙임2] ⑤:

> `rspn_tp`이 **"01"인 경우 전자상거래업자 검증 지원용으로 앞 2자리 숫자 제공**

공식 예시 응답이 `"su_crtf_no": "72"` 입니다. 6자리 전체는 **수하인의 이메일로만** 발송되고, 쇼핑몰은 `eml_addr`로 마스킹된 주소(`t*****@korea.kr`)만 안내받습니다.

따라서 일반 경로에서 쇼핑몰이 해야 할 일은:

1. 고객에게 **인증번호 6자리 입력 UI를 노출**
2. 1차 검증 — 입력값 앞 2자리 == 관세청이 준 2자리
3. 2차 검증 — **체크디지트 자체 계산**
   - 수하인 전화번호 끝 4자리 + 인증번호 앞 5자리 = 9자리
   - (홀수자리 합)×3 + (짝수자리 합) → mod 10 → 10에서 뺀 값 == 인증번호 6번째 자리
   - 예: 전화 `01000001234`, 인증번호 `567895` → `123456789` → (1+3+5+7+9)×3+(2+4+6+8)=95 → 95%10=5 → 10−5=5 → 끝자리 5 일치

기획서에는 이 UI도, 이 알고리즘도 없습니다. **Stage 1이 통과하지 못하므로 Stage 2 이후는 실행되지 않습니다.**

### 왜 지금까지 문제가 드러나지 않았나 (중요)

사업소개 v1.6의 단계적 적용 일정을 보면 2026년에는 상당수 주문이 우연히 통과합니다.

| 기간 | 적용 범위 |
|---|---|
| 26.2 ~ 26.8.15(오픈 전) | 통관정보 검증강화 (성명·전화·우편번호 일치 검증) |
| **26.8.15 ~ 26.12.31** | **신규발급·정보변경 국민만** 인증번호 검증체계 적용 |
| 27.1.1 ~ 28.1.31 | 생일 기준 순차 확대. 협력인정업체 직접 제공은 **'27.2.1부터** |
| 28.2.1 ~ | 전 국민 전면 적용 |

검증체계 **비대상** 국민(= 아직 갱신 안 한 기존 부호 보유자)은 `rspn_tp=03`으로 응답되고, 이때는 **6자리 전체가 그대로 옵니다**(사용자 입력 절차 불필요).

즉 **2026년에는 다수 주문이 6자리를 받아 정상 동작하고, 신규·정보변경 고객만 조용히 실패합니다.** 그리고 2027년부터 실패 비율이 계속 올라가 2028-02-01에 전면 붕괴합니다. 지금 구조는 **시한폭탄**입니다. `rspn_tp` 분기를 처리하지 않으면 실패 원인조차 잡히지 않습니다.

### Stage 3 — TRA001 제출 · **전체 반려**

`ord_site_url`(주문 사이트 인터넷 주소, **String(200) 필수**)이 기획서 63개 항목에 **아예 없습니다.** v1.4.1 TRA001 사용 제약:

> 아래 항목을 검증하여 오류가 있는 경우 **전체 반려됨** … 3. 요청데이터의 형식이 잘못된 경우

여기에 스키마에 존재하지 않는 필드 8개(`hs_cd`, `ord_qty_ut`, `tot_wt`, `stlm_mns_cd`, `stlm_dttm`, `insrc_amt`, `tax_amt`, `ordrr_email`)를 함께 전송하도록 설계되어 있습니다. 화이트리스트 직렬화가 아니면 요청 거부 위험이 큽니다.

또한 제출 시각이 **10:00~11:00**인데, 간담회 안건에서 관세청은 명시적으로 요청했습니다.

> 신고서 등의 제출이 많은 **9~18시를 제외한 시간으로 거래정보 제출시간 분산 요청**

기획의 배치 시각이 관세청이 피해달라고 한 구간 한복판입니다.

### Stage 4·5 — TRA003 오류조회 · **거짓 성공**

주문 단위 오류건수가 0이어도 상품 단위 오류가 남아 있을 수 있습니다. 현재 설계는 이 경우를 100% 놓칩니다.

## 3. 신규 치명 결함

### 3.1 협력인정업체 자격이 전제 없이 가정되어 있음

간소화 인증(팝업 없음)의 조건은 세 개가 **동시에** 성립할 때뿐입니다.

1. 관세청에 **협력인정업체로 선정**된 업체일 것 (UNI-PASS 기업포털에서 신청)
2. **주문자와 수하인의 성명·전화번호가 동일**할 것
3. 주문자 **CI** 전송

하나라도 어긋나면 에러이거나 일반인증으로 강등됩니다.

| 코드 | 출처 | 의미 |
|---|---|---|
| 3100 | 관세청 | 해당 전자상거래업자부호는 협력인정업체용 요청을 할 수 없음 |
| 3110 | 관세청 | 주문자와 수하인이 다른 경우 협력인정업체용 요청 불가 |
| 0004 | NICE | 간소화 이용불가 업체(**협력인정업체 아님**) |
| 0005 | NICE | 간소화 이용불가 업체(주문자/수하인 불일치) |

**K26000099(크로네)가 현재 협력인정업체로 등록되어 있는지 확인된 문서가 폴더에 없습니다.** 사업소개상 협력인정업체 직접 제공은 '27.2.1부터이고, 2026년에는 "CI 제공이 가능한 전자상거래업자"에게 제공하되 **'27.1.31 협력인정업체 선정 전까지**라는 단서가 붙어 있습니다. 이 자격의 현재 상태가 A안 전체의 성립 여부를 결정합니다. **최우선 확인 항목입니다.**

선물 주문(주문자≠수하인)은 자격과 무관하게 **항상** 일반인증으로 떨어집니다. 따라서 **일반인증 경로는 선택이 아니라 필수 구현**입니다. NICE 가이드도 명시합니다.

> 간소화 인증 시 주문자/수하인 정보가 다르거나, 간소화 업체가 아닌 경우 **일반인증방식으로 전환**

"간소화만 만들고 끝"이 불가능하다는 뜻입니다.

### 3.2 일회용 개인통관부호(`su_pers_cscl_sgn`)가 설계에 없음

협력인정업체 경로의 응답에는 인증번호와 **함께** 일회용 개인통관부호가 옵니다.

```
"su_info": { "su_crtf_no": "551860", "su_pers_cscl_sgn": "O261114881614" }
```

사업소개 정의:

> 일회용 개인통관부호란? 전자상거래 물품 구매 시 주문자의 구매 편의를 위해 **개인통관고유부호 작성 없이** 구매 및 통관이 가능하도록 관세청이 협력인정업체로 등록된 사이버몰 운영업체에게 직접 발급하는 부호

NICE SMARTPCC_11 응답의 `pers_ecm`도 "개인통관부호 **or 1회용 개인통관부호**"입니다. 즉 간소화 경로에서는 고객의 진짜 PCCC 대신 `O`로 시작하는 일회용 부호를 받게 됩니다.

**그런데 기획서에는 이 필드가 없고, TRA001 `cnsi_pers_ecm`과 자이언트 `pccCode`에 무엇을 넣어야 하는지 정의가 없습니다.** 진짜 부호인지 일회용 부호인지에 따라 통관 결과가 갈립니다. 서면 확인 필요.

### 3.3 `Z99999`는 어떤 공식 문서에도 존재하지 않음

전수 검색 결과입니다.

| 문서 | Z99999 |
|---|---|
| 관세청 REST API 명세서 v1.4.1 | **0건** |
| 개인통관고유부호 CI 활용 가이드 (NICE) | **0건** |
| 통관플랫폼 사업소개 v1.6 | **0건** |
| 전자상거래업자 간담회 안건 | **0건** |
| 계약서 / 가견적서 | **0건** |
| planning_v5.html, api_field_mapping.html (+중문판) | 다수 |

**우리 기획 문서에서만 나옵니다.** 기획서는 이를 "계도기간 유예코드"로 설명하고 `su_crtf_no`와 자이언트 `tempAuthNo`에 대체 주입하도록 되어 있는데, 근거가 없습니다.

혼동의 원인으로 추정되는 실제 규정은 간담회 안건의 **다른 내용**입니다.

> 기존 통관목록 서식(GOVCBR936)으로 제출. 거래유형 항목 값을 "**A(전자상거래물품)**"로 제출. (A 값은 **시스템 오픈 후 1개월간 유효**)

이것은 **장애 시 기존 서식 폴백에서 쓰는 거래유형 코드**이고, 인증번호와 무관합니다. `Z99999`를 인증번호 자리에 넣는 설계는 즉시 폐기해야 합니다.

|---|---|---|
| A | **구매대행** | 네이버스토어(아이베), 기타 외부 쇼핑몰 |
| B | **직접판매(전자상거래)** | 크로네 자사몰 |

같은 문서 3절 매트릭스:

| 채널 | elcm_pcd |
|---|---|
| 크로네 자사몰 | **A (직접판매)** |
| 네이버스토어 | **B (구매대행)** |

공식 v1.4.1은 `A: 직접판매 / B: 구매대행 / C: 배송대행`입니다. **1절이 틀렸고 3절이 맞습니다.** planning_v5와 api_field_mapping은 3절과 같은 올바른 값을 쓰고 있습니다.

문제는 이 문서가 중문판으로도 번역되어 동수·자이언트에 공유됐다는 점입니다. 1절만 보고 구현하면 전 건의 판매유형이 뒤집히고, 그에 딸린 `puch_vcex_bsmn_sgn` 필수 조건과 `sale_ents_nm` 필수 조건이 전부 반대로 적용됩니다. **최우선 정정 대상입니다.**

### 3.5 개인정보 고지와 실제 전송 항목 불일치

## 5. NICE 경로 대조

### 5.1 두 개의 서로 다른 NICE 서비스

2026-08-06 카톡의 혼선은 정리하면 이렇습니다. **박종혁님의 Step 1/Step 2 정리가 맞습니다.**

| | 서비스 | 도메인 | 용도 |
|---|---|---|---|
| Step 1 | **NICE 통합인증** | `auth-guide.niceid.co.kr` | 휴대폰 본인확인 → **`ci` 획득** |
| Step 2 | **NICE SMARTPCC** | `smartpcc.niceid.co.kr` | `ordrr_key`에 CI 담아 PCCC 검증 → `pers_ecm` + `otp` |

별개 제품이고 **client_id/secret도 별도, 방화벽 대상 도메인도 별도, 암복호화 구현도 별도**입니다.

김동섭님의 "NICE 검증 진행하면 NICE가 본인인증 팝업을 노출하는 구조로 이해했다"도 절반은 맞습니다. **일반인증(svc_type=B)에서는 SMARTPCC_10이 `auth_url`을 반환하고 NICE가 SMS/이메일 점유확인 팝업을 띄웁니다.** 별도 개발이 필요한 것은 **간소화(svc_type=A)용 CI를 얻기 위한 통합인증**뿐입니다.

이는 공수 산정에 직접 영향을 줍니다. 8/7 오후 2:08 견적(4일)은 통합인증 개발 + 브랜드/버전별 화면 반영 기준으로 보이는데, 아래가 포함됐는지 확인이 필요합니다.

- 일반인증(`svc_type=B`) 팝업 + 콜백 + 결과조회 경로 — **간소화 자동 강등 때문에 필수**
- `rspn_tp` 01/02/03 3분기 처리
- 직접 연동 시 OTP 입력 UI + 체크디지트 검증
- PER002 재검증 / PER003 사후처리
- **CI 생애주기 관리** — 박종혁님이 우려한 번호변경·개명 시 CI 갱신 루프
- AES/GCM + PBKDF2 KDF + HMAC 무결성 검증 (통합인증·SMARTPCC 각각)
- NICE에 Outbound IP 등록 (D/C-Class, 클라우드는 NAT 단일 IP)

### 5.2 NICE ↔ 관세청 가이드 간 불일치

구현 전에 NICE에 확인해야 할 항목입니다.
