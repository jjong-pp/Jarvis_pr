1. 결론

현재 7개 persona 구조는 폐기할 대상이 아니라 운영체계의 뼈대다. 새로 개발현황, 마케팅현황, 자금정책현황 폴더를 병렬로 만들면 같은 사실이 기존 persona와 중복된다.

권고 구조는 다음과 같다.

  1. 기존 7개 persona를 현황 정본을 책임지는 도메인 에이전트로 승격한다.
  2. 빠진 고객성공·지원·갱신 책임은 먼저 기존 SAL·PRD·TEC 중 주 담당을 정하고, 유료 고객 운영량이 생길 때 8번째 도메인으로 분리한다.
  3. 개발·GTM·자금정책 같은 종합 현황은 새 정본 폴더가 아니라 여러 도메인을 합친 대시보드 뷰로 만든다.
  4. 폴더, 에이전트, 스킬, MCP를 서로 다른 계층으로 둔다.

폴더  = 지속되는 사실·상태·이력의 정본
에이전트 = 해당 정본을 읽고 판단·갱신하는 역할
스킬  = 여러 에이전트가 반복해서 따르는 공정
MCP   = 외부 시스템의 데이터·도구 접근 통로
대시보드 = 정본을 복제하지 않는 사람용 종합 화면

폴더만 만든다고 자동으로 에이전트가 되지는 않는다. 역할 경계, 입력·출력 계약, 도구 권한, 완료 조건을 함께 정의해야 한다.

7. 에이전트 동작 계약


입력
  → 총괄이 주 담당 1개·검토 역할을 라우팅
  → 주 담당이 자신의 inbox/research/state/output만 갱신
  → 검토 역할은 반증·리스크·숫자 근거를 제시
  → 역할 충돌은 control/08 결정 대기 항목으로 승격
  → 전사 결론만 control/에 반영
  → 빌드 스크립트가 사람용 대시보드 생성

초기 권한은 다음처럼 둔다.

  • 도메인 에이전트: 기본 읽기 전용, 자기 폴더 변경안과 근거를 반환
  • 총괄 에이전트: 검토 후 persona와 control/에 증분 반영
  • 룰·스킬·에이전트 정의: 총괄만 수정
  • 외부 게시·메일·광고·결제·계약·고객 데이터 변경: 사람 승인 필수
  • 병렬 에이전트: 서로 독립적인 읽기·조사·검토에만 사용하고 같은 정본의 동시 쓰기는 금지

운영이 안정되면 도메인 에이전트가 자기 폴더만 직접 갱신하도록 확대할 수 있다. control/, 룰, 계약, 외부 쓰기는 계속 총괄·사람 게이트를 둔다.

8. 프로젝트 룰 초안

기존 AGENTS.md를 늘리기 전에 아래 중 사고 방지에 필요한 항목만 승격한다.

  1. 한 사실은 한 정본에만 두고 다른 화면은 링크한다.
  2. 숫자·금액·날짜·법령·정책·필드명은 출처와 확인일을 붙인다.
  3. 모르는 값은 0으로 바꾸지 않고 미확인으로 둔다.
  4. 정정·전략 변경은 종전 내용을 삭제하지 않고 대체 ID와 이유를 남긴다.
  5. 과업마다 주 담당 하나와 필요한 검토 역할만 둔다.
  6. 외부 조사 결과는 공식 1차 출처와 최신성을 확인하기 전 확정하지 않는다.
  7. 외부 발송·게시·광고·결제·계약·고객 데이터 변경은 사람 승인 후 실행한다.
  8. 재무·법률·개인정보·보안·가격 결정은 에이전트가 자동 확정하지 않는다.
  9. 전사 판단만 control/에 승격하고 역할별 근거는 persona에 둔다.
  10. 대시보드는 MD 정본에서만 생성하며 생성 HTML을 직접 고치지 않는다.

9. 스킬 설계

역할마다 스킬을 하나씩 만들지 않는다. 역할은 사용자 정의 에이전트가 맡고, 스킬은 반복 공정만 맡는다. 스킬은 이름·설명으로 필요할 때 로드되므로 한 스킬을 한 작업에 집중시킨다.

기존 market-bigsee 스킬은 사업 정본 라우팅과 절대 규칙을 유지한다. 같은 내용을 새 스킬에 복제하지 않는다. 실제 생성 시 지침 중심으로 시작하고, 스키마 검사·대시보드 검증처럼 결정론이 필요한 반복 작업만 스크립트로 둔다.

10. MCP·플러그인 설계

MCP는 에이전트를 만드는 도구가 아니라 외부 시스템을 읽고 행동하게 하는 통로다. 연결은 데이터가 실제로 존재하는 곳부터 최소 권한으로 연다.

단계연결 후보목적초기 권한도입 조건
1GitHub코드·이슈·PR·릴리스·배포 이력읽기 전용개발 저장소와 운영자의 정보권 합의
1Browser/Web정부·법령·커뮤니티·경쟁사 공식 출처 확인읽기 전용출처·확인일 저장 규칙 적용
2Google Drive 또는 SharePoint회의록·계약·자문 산출물 검색읽기 전용실제 정본이 그곳에 있을 때만
2Gmail/Outlook, Calendar개발자·자문가 회의와 회신 대기 추적검색·초안, 발송 승인채널 선택과 개인정보 범위 합의
2Slack 또는 Teams결정·질문·회신 후보 수집검색 중심실제 협업 채널일 때만
3BIGSEE 내부 읽기 API/MCP활성·퍼널·UsageLedger·원가·오류·결제 조회읽기 전용인증·감사·개인정보 최소화·관리 API 완성
후순위Figma제품 흐름·화면 검토읽기 중심실제 디자인 정본이 Figma일 때

Notion 등 새 도구를 정본으로 추가하지 않는다. 현재 Git/Markdown 정본을 유지하고 외부 도구는 원자료 수집과 실행 채널로만 쓴다.

BIGSEE 내부 MCP를 만든다면 처음에는 조회 도구만 둔다.


get_product_status
list_releases_and_incidents
get_active_user_funnel
get_usage_cost_summary
get_customer_health
get_cashflow_snapshot

사용자·결제·광고·게시·환불을 변경하는 도구는 1차 범위에서 제외한다. MCP 서버는 공식 제공자를 우선하고, 도구 allowlist를 쓰며, 읽기 외 동작은 승인 모드로 둔다.
