1. 사용자의 역할과 최종 목적

사용자는 BIGSEE의 개발자가 아니다. 제품을 총괄 개발한 사람이 개발에 집중할 수 있도록 다음 영역을 맡아 사업을 실제로 굴리려는 운영자다.

  • 서비스 분석과 시장·경쟁 판단
  • 판매 전략과 채널 운영
  • 마케팅 자문과 광고 집행 설계
  • 고객 인터뷰·영업·후속·고객 성공
  • 가격·원가·현금흐름·CAC 관리
  • 개발자에게 전달할 제품·계측 우선순위 정리
  • 장기적으로 파트너십·보상·의사결정 구조 협상

최종 목적은 문서를 많이 만드는 것이 아니라 누가 어떤 상황에서 BIGSEE에 돈을 내고 반복해서 쓰는지를 찾고, 그 증거로 제품·가격·마케팅·파트너십을 결정하는 것이다.

2. 처음 확인한 서비스

공개 페이지 기준 BIGSEE는 네이버·YouTube·Google·Instagram·뉴스의 키워드와 마케팅 자료를 모아 CSV·HTML·AI 결과물로 정리하는 국내 멀티채널 마케팅 리서치 SaaS다.

공개 페이지:

  • 소개: https://market-bigsee.com/about.html
  • 가격: https://market-bigsee.com/pricing
  • 환불: https://market-bigsee.com/refund
  • 개인정보: https://market-bigsee.com/privacy
  • 이용약관: https://market-bigsee.com/terms

2026-08-13 공개 페이지에서 정리한 요금은 무료, Pro 29,900원, Premium 59,900원, Enterprise 199,900원, 토큰 1개 3,900원이다. 이 값은 공개 페이지 스냅샷이며 다음 세션에서 현재 가격으로 단정하지 말고 필요하면 다시 확인한다.

공개 문서로 추정한 기술은 Google 로그인, Netlify/Functions, Firebase, Naver·YouTube·Google Ads·Instagram/Meta·뉴스·AI 계열 외부 API다. 실제 저장소·DB·배포·청구서·API 계약은 한 번도 확인하지 않았다.

초기 사업성 평가는 67/100이었다. 실제적인 멀티채널 조사 문제와 국내 플랫폼 통합은 장점이나, 반복 사용·성과 입증·원가·팀 기능·데이터 방어력·외부 API 의존이 약점이라는 평가다. 이 점수는 공개 정보 기반 초기 스코어이므로 투자·가격·광고 결정을 확정하는 숫자가 아니다.

3. 처음부터 답하지 못한 핵심 질문

사용자는 가격 하한·요금제·B2B 판매·광고 규모를 정하기 위해 다음을 물었다.

  1. 사용자 1명이 한 달 쓰면 서버·외부 API 등 직접원가가 얼마인가
  2. 사용자가 늘 때 무료 구간·쿼터·인프라 때문에 비용이 계단식으로 튀는 구간이 있는가
  3. 현재 코드에서 횟수·용량·시간·좌석 등의 사용량을 측정할 수 있는가
  4. 기능 잠금·해제와 3단계 요금제 구현이 가능한가
  5. 개인 계정인지 조직·팀 계정 구조가 있는가
  6. 현재 인프라가 몇 명을 감당하고 1,000명에서 무엇이 먼저 막히는가
  7. 지금 유료 판매에 이른 부분은 무엇인가
  8. 개발자가 처음 상상한 구체적인 사용자는 누구이며 언제 제품을 켜는가

현재까지 공개 페이지만 보았으므로 이 질문의 정확한 답은 하나도 확정되지 않았다. 특히 원가, 계단식 비용, 기능 게이팅, 조직 경계, 1,000명 용량은 코드·로그·공급자 계약·청구 정보 없이는 계산할 수 없다.

다음 로컬은 추정치를 사실처럼 채우지 말고 개발자에게 다음 데이터를 받아야 한다.

  • 실제 사용자·테스트·관리자 계정 구분
  • 7일/28일 핵심 활성, 첫 리포트, 반복, 유료, 환불
  • 외부 API/AI별 요청·토큰·성공·실패·재시도·처리시간·비용
  • Functions·DB·저장·전송·결제 수수료와 무료 구간·쿼터
  • user/workspace/project 데이터 모델과 서버 측 권한 검사
  • 기능별 차감·잠금 위치와 동시성·중복 차감 방지
  • 현재 장애·백업·알림·보존·개인정보 삭제 구조

4. 사용자 약 20명이라는 정보

개발자 측에서 이미 사용자 약 20명이 있다는 정보가 추가되었다. 이것은 사용자가 전달한 값일 뿐 다음이 구분되지 않았다.

  • 실제 사람인지 테스트·관리자·중복을 포함하는지
  • 최근 7일·28일에 핵심 행동을 했는지
  • 한 번 체험했는지 반복 사용하는지
  • 무료인지 실제 수금된 유료인지
  • 대행사·인하우스·셀러·기타 중 누구인지
  • 어떤 경로로 들어왔고 무엇을 위해 사용했는지
  • 한 사람당 직접원가와 지원시간이 얼마인지

따라서 20명은 광고 성과의 증명이 아니라 가장 먼저 연락하고 관찰할 고객 연구 집단이다. 기존 로그에서 알 수 없는 값은 0이 아니라 unknown으로 기록한다.

필수 백필·이벤트 구조는 personas/04_sales_marketing/reference/16_existing_user_measurement_ad_pilot.md에 있다. 다만 그 문서의 검색광고 우선·Meta 리타게팅 채널 순서는 현재 폐기되었고, 사용자 계측·원가 원장 부분만 유효하다.

5. 사용자가 처음 생각한 판매·마케팅 방향

사용자는 Meta의 Instagram·Facebook, TikTok, Naver, Google 광고로 B2C 고객을 먼저 확보하고 이후 B2B로 들어가는 방향을 생각했다. 이때 자동 블로그 홍보 글, SKU 등록, 판매성과 측정, 이후 공개 API와 타사 연동도 함께 구상했다.

이 생각의 유효한 핵심은 다음이었다.

  • 자료 조사만으로 끝내지 않고 조사 결과를 실제 홍보 행동으로 전환
  • 상품 단위인 SKU를 넣어 콘텐츠와 판매를 연결
  • 광고·콘텐츠·리드·매출을 측정하는 운영 시스템 구축
  • 개인 사용에서 팀·대행사 계약으로 확장
  • 장기적으로 다른 시스템이 BIGSEE 데이터를 사용할 수 있게 API 개방

초기 접근의 위험은 고객이 아직 특정되지 않은 상태에서 네 채널을 동시에 넓게 집행하고, 사용량·첫 가치·결제 추적 없이 가입자를 늘릴 수 있다는 점이었다.

6. 전략이 여러 번 바뀐 과정과 이유

6-1. 첫 분석: 대행사 중심 가설

처음에는 여러 고객의 제안서·캠페인을 반복 조사하는 2~20인 광고·마케팅 대행사가 빈도·지불의사·팀 확장 면에서 가장 유력하다고 보았다. 기능이 아니라 제안서용 조사 결과를 판매한다는 방향은 지금도 유효하다.

그러나 기존 사용자 20명의 구성과 실제 결제가 없으므로 대행사를 확정 고객으로 선언하는 것은 근거가 부족했다. D-001은 이후 대체되었다.

6-2. 검색광고 우선안

기존 약 20명 계측 후 Naver·Google 검색을 먼저 4주 시험하고 Meta는 리타게팅으로 쓰는 안이 만들어졌다. 검색은 문제 인지가 있는 수요를 잡는 장점이 있지만, 사용자는 이 접근이 본인이 원하는 대형 커뮤니티 배포와 Meta 발견형 수요 검증을 반영하지 못한다고 보았다.

이 안의 이벤트·원가 계측은 남기고 채널 순서는 폐기했다.

6-3. 운영자 중심 리셋과 순차 커뮤니티→Meta안

그다음 문서 관리와 광고 집행표보다 고객·매출·현금·개발 협업을 먼저 보는 운영자 관점으로 바꾸었다. 기존 사용자 인터뷰, 직접 판매, 커뮤니티, Meta 순서로 위험을 줄이려 했다.

사용자는 이 역시 마케팅 대상과 타깃을 정확히 정의하지 않은 채 실행 순서만 정한 것이라고 지적했다. 특히 큰 커뮤니티에 배포하면서 Meta를 동시에 돌려야 하고, 제품 기획도 함께 바뀌어야 한다고 명시했다.

6-4. 현재안: 업무·구매상황 페르소나와 커뮤니티×Meta 동시 시험

현재는 인구통계나 막연한 B2C가 아니라 최근 30일의 실제 업무, 반복 빈도, 금전 결과, 구매자, 기존 대안으로 타깃을 정의한다.

  1. 1순위 가설: 광고대행사 전략·퍼포먼스 실무자와 팀장
  2. 비교군: 이커머스 브랜드 인하우스 성장·콘텐츠 마케터
  3. 비교군: 이미 상품과 광고비가 있는 다채널 셀러

대행사가 1순위인 이유는 여러 고객의 제안·보고·경쟁조사가 반복되고 고객 워크스페이스·좌석·승인으로 팀 계약이 확장될 가능성이 높기 때문이다. 이것은 아직 고객 행동으로 증명되지 않은 가설이다.

예비 창업자, 취미 블로거, 판매 상품이 없는 사람, 허위 리뷰·순위 조작 수요, 즉시 SSO·SLA가 필요한 대기업은 초기 광고 대상에서 제외한다.

7. 현재 마케팅 전략

채널

  • 아이보스: 광고대행사·인하우스 마케터의 실무 조사·제안서·콘텐츠·데이터 맥락
  • 셀러오션: 이미 쇼핑몰을 운영하는 셀러의 SKU 출시·광고·콘텐츠 맥락
  • Meta Leads/Instagram Direct: 동일 페르소나와 동일 제안을 더 넓게 발견하고 상담으로 연결
  • 아프니까 사장이다: 범위가 너무 넓어 현재 핵심이 아니라 후순위 보조 후보
  • Naver·Google 검색: 페르소나와 검색 표현이 확인된 후 확장 후보
  • TikTok: 숏폼 메시지와 소재가 검증되기 전에는 제외

실행 방식

커뮤니티를 끝낸 뒤 Meta를 하는 것이 아니다. 세 페르소나별로 같은 샘플·랜딩·제안을 만들고 아이보스·셀러오션과 Meta에 같은 14일 동안 배포한다.

커뮤니티 게시물은 문제·분석 과정·샘플·한계·진단 CTA의 교육형 자료로 만들며 위장 홍보, 자동 살포, 가짜 후기, 규정 위반을 하지 않는다. 유료 배너·네이티브·뉴스레터·웨비나는 2026년 공식 규정과 견적을 다시 받아야 한다. 검색되는 과거 아이보스 제안서는 2018년 자료라 현재 가격으로 사용할 수 없다.

Meta는 작은 예산에서 캠페인을 과도하게 쪼개지 않고 Leads 또는 Instagram Direct 캠페인 1개, 필요할 때 광고 세트 1~2개, 페르소나별 소재 3개를 기본 가설로 둔다. 관심사 타기팅은 확장될 수 있으므로 광고 문구와 폼의 역할·최근 업무·고객/SKU 수·다음 일정으로 자격을 확인한다.

판단 지표

landing_view → sample_request → qualified_lead → demo → report_completed → pilot_paid → week4_active → team_invite

클릭률·싼 CPL은 보조 지표다. 최종 판단은 유효 상담, 자기 데이터로 첫 리포트 완성, 실제 수금, 4주 반복, 팀 신호, 지원 공수다.

현재 예산

첫 14일 사업개발비 상한 가설은 150만~300만원이다.

  • Meta 70만~120만원
  • 커뮤니티 공식 집행·협찬 50만~100만원
  • 랜딩·샘플·소재·인터뷰 보상·측정 30만~80만원

이는 시장 평균이나 확정 예산이 아니라 멈출 수 있는 내부 산술 상한이다. 현금 잔액·부가세·비용 부담·공식 견적·후속 인력을 확인한 뒤 개발자와 항목별 승인해야 한다. 과거 문서의 55만~130만원 운영비 또는 검색광고 150만원안은 현재 채널 계획이 아니다.

9. 제품 기획이 바뀐 과정

사용자가 처음 제안한 기능

  • 조사 결과로 블로그 홍보 글 자동 작성
  • SKU 등록 화면
  • Salesforce처럼 판매 흐름과 성과를 측정
  • 장기적으로 API를 열어 타사 시스템과 연동
  • 숏폼·릴스 자동 제작은 당장은 어렵지만 이후 검토

해석과 현재 제품 방향

블로그 생성기를 별도 AI 글쓰기 도구로 만들면 범용 생성 AI와 차별이 약하고 저가치 대량 콘텐츠 위험이 있다. 따라서 조사 근거, SKU 승인 사실, 타깃, 브랜드 문체, 금지 표현을 입력으로 쓰고 사람이 승인한 뒤 캠페인과 매출에 연결해야 한다.

세일즈포스 측정은 Salesforce 전체를 복제하는 것이 아니라 광고·커뮤니티 리드가 어느 영업 단계에서 멈추는지 보는 경량 CRM으로 정의했다.

현재 제품 루프:

워크스페이스/고객 → SKU → 조사 브리프 → 근거 → 홍보 초안 → 승인 → 캠페인/추적 링크 → 리드/구매 → 사용량/원가 → 다음 실행

P0 판매 MVP

  • 조직·고객 워크스페이스와 기본 권한
  • SKU 직접 입력·CSV·채널 상품 ID
  • 조사 브리프와 출처·수집일·비용 기록
  • 블로그·Meta·커뮤니티·이메일/DM 초안
  • 사람 승인·버전·주장/금지표현 검사
  • 캠페인·UTM·추적 링크와 기본 이벤트
  • Lead·Account·Opportunity·Activity 중심 경량 CRM
  • 사용자·워크스페이스·기능·공급자별 UsageLedger

P1

  • 팀 역할·초대·고객 프로젝트·승인
  • Meta Lead 동기화와 Conversions API
  • GA4 이벤트 보완
  • 카페24 등 실제 파일럿 고객이 쓰는 첫 커머스 연동
  • 팀 리포트

P2

  • Public API v1
  • API key/OAuth, scope, rate limit, idempotency, 감사 로그
  • 버전·샌드박스·문서·사용량 과금
  • 추가 광고·커머스·CRM 커넥터

현재 제외

  • 자동 대량 게시
  • 가짜 리뷰·순위 조작
  • Salesforce 전체 복제
  • 모든 쇼핑몰 동시 연동
  • 숏폼 영상 자동 렌더링
  • 충분한 데이터가 없는 고급 다중접점 기여도

P0 4~6주, P1 6~10주는 풀스택 개발자 1명과 기획 지원을 가정한 범위 가설이다. 실제 코드·인증·DB·권한·이벤트 구조를 보기 전 확정 일정이 아니다.

10. 가격·원가·인프라에 대한 현재 생각

현재 공개 요금표를 그대로 광고 확대로 연결하면 안 된다. 다음 계산이 먼저다.


고객당 월 직접원가
= Functions/compute/전송
+ DB read/write/storage
+ 플랫폼 API 비용
+ AI 입력·출력 토큰
+ 결제 수수료
+ 고객지원 배부액

예상되는 첫 병목은 일반 CPU보다 YouTube·Naver·Google Ads·Meta 등 외부 쿼터, AI 비용·지연, DB 쿼리 구조, 고객지원일 가능성이 높다. 그러나 이는 추정이다.

요금제는 장기적으로 좌석, 고객 워크스페이스, 활성 SKU, 월 조사/콘텐츠, 연결 스토어, 이벤트 처리량, 외부 API, 보존기간, 리포트 브랜딩을 혼합할 수 있다. 실제 하한과 포함량은 UsageLedger가 2주 이상 쌓이고 유료 파일럿의 지원 공수를 본 뒤 정한다.

11. 15% 보상·파트너십 문제

제품을 총괄 개발한 사람은 판매 건당 15%를 제안했다. 사용자는 단순 리베이트 판매자가 아니라 판매 전략·광고·CRM·영업·운영을 세팅하는 역할이므로 이 구조가 마음에 들지 않는다고 했다.

현재 객관적 판단은 다음과 같다.

  • 고객 소개만 하면 실제 수금 순매출의 15%는 가능한 리퍼럴 모델이다.
  • 전략·광고·퍼널·CRM·고객 성공까지 지속 운영하면 일회성 건당 15%만으로는 역할 분류가 맞지 않을 수 있다.
  • 개발자는 코드·제품·기술부채·장애·보안 등 더 큰 선행 투자를 보유한다.
  • 사용자는 아직 반복 매출과 재현 가능한 CAC를 만들지 않았으므로 전략 문서만으로 즉시 동등 지분을 요구할 근거도 부족하다.
  • 가장 합리적인 구조는 90일 성과계약 후 권리와 보상을 단계적으로 올리는 방식이다.

최소 합의 항목:

  • 실제 입금액 - 부가세 - 환불 - 차지백 기준 순매출 정의
  • 직접 발굴·광고·기존 고객의 매출 귀속
  • 최초 매출뿐 아니라 갱신·업셀 인정 기간
  • 광고·도구·콘텐츠 비용의 별도 정산
  • CRM·결제·환불·사용량·정산 열람권
  • 가격·할인·환불·광고문구 협의권
  • 광고 계정·CRM·소재·GTM 문서의 소유·사용권
  • 종료 후 이미 확보한 고객의 tail과 인계
  • 역할·성과에 따른 기본 운영비·반복매출·의사결정권·지분/이익배분 승급

조건 합의 전에는 전체 캠페인 운영서·CRM 구조·소재·가격 실험 자산을 모두 넘기지 않고 1~2페이지 요약 전략과 가치만 공유하는 것이 안전하다는 판단이다.

상세 정본: personas/01_strategy_ceo/reference/14_gtm_compensation_partnership_framework.md

13. 대시보드와 문서 구조가 바뀐 이유

처음에는 하나의 dashboard/index.html 안에 모든 사업 내용을 내비 태그와 접기/펼치기로 합쳤다. 사용자는 내용이 길어지고 판단 영역이 섞이므로 폴더를 만들고 여러 HTML이 서로 연결되기를 명시적으로 요청했다.

현재 구조:


dashboard/
├─ index.html                 개요
├─ pages/
│  ├─ personas.html          타깃
│  ├─ launch.html            시장진입

사람은 연결형 HTML을 보지만 사업 사실은 MD에서만 수정한다. HTML은 scripts/build-dashboard.ps1로 생성하며 직접 수정하지 않는다. D-011 단일 HTML 결정은 D-014로 대체되었다.

토큰 절약은 HTML을 하나로 만드는 데서 나오지 않는다. 다음 로컬이 README → 이 인계 문서 → SECTION_REGISTRY → 요청과 맞는 정본 하나만 읽는 선택 로딩에서 나온다.

15. 현재 가설과 증거 수준

현재 사실

  • 공개 페이지상 멀티채널 마케팅 리서치 기능과 요금제가 존재한다.
  • 사용자가 전달한 정보로 등록 사용자가 약 20명이라고 한다.
  • 개발자가 건당 15%를 제안했다.
  • 현재 로컬에 타깃·시장진입·제품·운영·결정 정본과 생성 대시보드가 있다.

강한 가설

  • 광고대행사는 반복 조사와 팀 확장이 있어 가장 유망할 수 있다.
  • 조사 근거·SKU·콘텐츠·추적·CRM을 연결하면 단순 조사보다 유료 가치가 커질 수 있다.
  • 큰 실무 커뮤니티와 Meta의 동일 제안 동시 시험이 빠른 타깃 비교에 적합하다.

아직 증거가 없는 것

  • 어떤 페르소나가 실제로 가장 많이 결제하고 반복하는지
  • 20명 중 실제 활성·유료·반복 사용자가 몇 명인지
  • 고객당 월 원가와 총마진
  • 광고 CPL·유효 상담 비용·CAC
  • 팀·워크스페이스를 실제로 원하는 고객 수
  • 블로그 초안이 게시·클릭·구매로 이어지는지
  • P0 기능의 실제 개발 공수
  • 현 인프라의 1,000명 수용 가능성
  • 15% 계약의 실제 계산·귀속·권리

가설 대장: control/09_validation_board.md

16. 현재 리스크

  • 타깃 검증 전에 제품 범위를 크게 개발하는 것
  • UTM·첫 가치·결제·원가 없이 광고를 집행하는 것
  • 커뮤니티에 위장 홍보나 자동 대량 게시를 하는 것
  • AI가 출처 없는 수치·효능·후기를 만드는 것
  • 원가를 모른 채 낮은 가격과 무제한 사용을 약속하는 것
  • 개인 계정 구조로 팀 데이터와 고객 데이터를 섞는 것
  • 정보권 없이 GTM 매출 책임과 광고비만 부담하는 것
  • 조건 합의 전에 전체 판매 자산을 개발자에게 넘기는 것
  • Enterprise라는 이름으로 SSO·감사·SLA 없는 제품을 판매하는 것
  • 오래된 커뮤니티 광고 가격이나 공개 요금제를 현재값으로 단정하는 것
