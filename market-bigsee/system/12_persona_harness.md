# 마켓빅시 페르소나 하네스 엔지니어링 규약

기준일: 2026-08-13

## 1. 목적

하나의 긴 대화가 전략·고객·제품·판매·재무·기술·리스크 판단을 섞지 않도록 역할별 작업 메모리를 분리합니다. 각 역할은 자기 범위에서 탐색하고 표준 출력만 전달하며, 최종 사업 상태는 `control/` 정본과 `dashboard.html`에서 취합합니다.

- 역할별 컨텍스트를 작게 유지해 토큰과 탐색 비용을 줄입니다.
- 누가 어떤 근거로 무엇을 판단했는지 추적합니다.
- 역할 간 충돌을 숨기지 않고 의사결정 항목으로 만듭니다.
- 조사 원문과 최신 결론을 분리합니다.
- 다음 로컬 환경에서도 동일한 입·출력 계약으로 작업을 재개합니다.

## 2. 전체 흐름

```text
사용자 피드백·새 사실
        ↓
../control/00_project_status.md와 personas/registry.md로 라우팅
        ↓
담당 페르소나 inbox.md
        ↓
탐색·검증 → research.md
        ↓
현재 작업 상태 → state.md / 최신 판단·제안 → output.md
        ↓
역할 간 충돌·의존성 검토
        ↓
전사 결론만 control의 00·08·09·15로 승격하고 상세 근거는 담당 persona의 reference에 유지
        ↓
scripts/build-dashboard.ps1 → dashboard.html
```

## 3. 폴더 계약

각 `personas/<persona>/` 폴더는 정확히 다음 네 파일을 유지합니다.

| 파일 | 역할 | 수정 규칙 |
|---|---|---|
| `inbox.md` | 사용자 요청·다른 역할의 전달·대기 과업 | 새 과업에 고유 ID를 부여하고 완료 후 상태만 변경 |
| `state.md` | 지금 하는 일·차단 요인·다음 행동 | 최신 상태만 유지하며 `## Harness State` 표 형식을 보존 |
| `research.md` | 탐색 경로·출처·관찰·반증 | 근거를 누적하고 사실·추론을 구분 |
| `output.md` | 현재 결론·근거·제안·결정 요청·인계 | 최신 합성 결과만 유지하며 `## Dashboard Output` 표 형식을 보존 |

대시보드는 `state.md`와 `output.md`만 읽습니다. `research.md` 전체를 대시보드나 새 세션에 넣지 않습니다.

## 4. 역할 라우팅

| 질문·변경 유형 | 기본 담당 | 함께 검토할 역할 |
|---|---|---|
| ICP·포지셔닝·사업 우선순위·투자 순서 | 전략·경영 | 고객·시장, 재무·가격 |
| 고객 문제·경쟁사·시장 규모·인터뷰 | 고객·시장 | 전략·경영, 세일즈·마케팅 |
| 기능·사용 흐름·활성화·제품 실험 | 제품·성장 | 기술·데이터, 고객·시장 |
| 리드·콘텐츠·제안·파일럿·채널 | 세일즈·마케팅 | 고객·시장, 제품·성장 |
| 원가·가격·마진·손익·비용 계단 | 재무·가격 | 기술·데이터, 전략·경영 |
| 코드·계측·API·인프라·권한·확장성 | 기술·데이터 | 제품·성장, 재무·가격 |
| 개인정보·약관·환불·AI 품질·운영 통제 | 리스크·운영 | 기술·데이터, 전략·경영 |

복합 입력은 하나의 주 담당만 정하고 나머지는 검토자로 둡니다. 같은 사실을 여러 폴더에서 독립 정본으로 만들지 않습니다.

## 5. 입력 계약

`inbox.md`의 새 과업에는 다음 항목을 포함합니다.

- 과업 ID: `<역할 코드>-NNN`
- 입력 날짜와 요청자
- 질문 또는 바뀐 사실
- 기대 산출물과 완료 기준
- 관련 control·reference 문서와 선행 역할 출력
- 시간·비용·권한·데이터 제약

불명확한 입력은 위험한 가정을 확정하지 말고 `state.md`의 `입력 대기`에 기록합니다.

## 6. 출력 계약

모든 `output.md`의 `## Dashboard Output` 표는 다음 필드를 유지합니다.

| 항목 | 의미 |
|---|---|
| 결론 | 현재 증거로 말할 수 있는 한 문장 |
| 근거 | 결론을 지지하는 가장 강한 증거 |
| 가설·한계 | 아직 확인되지 않은 조건과 반증 가능성 |
| 제안 | 다음으로 실행할 구체적 행동 |
| 의사결정 요청 | 사용자 또는 다른 역할이 선택해야 하는 사항 |
| 다음 전달 | 후속 역할과 필요한 입력 |
| 정본 링크 | 상세 근거가 있는 루트 또는 역할 문서 |

값이 없으면 삭제하지 말고 `없음`, `미측정`, `입력 대기` 중 하나로 표시합니다.

## 7. 정본 승격 규칙

- 페르소나 출력은 역할별 최신 판단이며 전사 확정 결정이 아닙니다.
- 고객 행동·실측 원가·코드 확인처럼 강한 증거가 생기면 담당 persona의 reference 문서에 반영합니다.
- 현재 단계·리스크·다음 행동이 바뀌면 `../control/00_project_status.md`를 갱신합니다.
- 선택이 확정되거나 기존 방향을 대체하면 `../control/08_decision_log.md`에 남깁니다.
- 실험 결과와 증거는 `../control/09_validation_board.md`에 연결합니다.
- 승격 후에도 연구 이력은 삭제하지 않습니다.

## 8. 충돌과 실패 처리

- 두 역할의 제안이 충돌하면 각각의 근거와 비용을 보존하고 `의사결정 요청`으로 올립니다.
- 출처가 없거나 최신성이 필요한 외부 사실은 확정으로 쓰지 않습니다.
- 작업이 막히면 `state.md`에 차단 요인·필요 입력·안전한 다음 행동을 기록합니다.
- 출력 형식이 깨지거나 필수 파일이 없으면 대시보드 빌드는 실패해야 합니다.
- HTML에서만 만들어진 사실은 무효입니다.

## 9. 토큰 로딩 규칙

총괄 작업은 `README.md → ../control/00_project_status.md → personas/registry.md → 관련 output.md` 순서로 읽고, 근거 확인이 필요할 때만 해당 `state.md`, `research.md`, 담당 persona의 reference 문서를 읽습니다.

개별 역할은 `personas/START_HERE.md → 자신의 inbox.md·state.md·output.md → 관련 control·reference 문서 1~2개 → 필요한 research.md 범위` 순서로 읽습니다.

AI는 생성물인 `dashboard.html`을 사업 정본으로 읽지 않습니다.

## 10. 대시보드 취합 규칙

- 페르소나 탭은 등록된 역할의 상태·현재 과업·결론·제안·결정 요청·다음 전달을 보여줍니다.
- 카드의 상세 링크는 해당 `state.md`와 `output.md`로 연결합니다.
- 사용자 피드백은 페르소나를 지정해 복사할 수 있어야 합니다.
- 빌드 해시는 루트와 `personas/` 아래의 모든 Markdown을 포함합니다.
- 대시보드는 결론을 새로 계산하지 않고 표준 출력을 표현만 합니다.

## 11. 완료 정의

1. 질문과 완료 기준에 답했습니다.
2. 가장 강한 증거와 가장 큰 한계를 함께 제시했습니다.
3. 다음 행동과 담당 역할이 정해졌습니다.
4. 의사결정 요청이 있다면 선택지가 명확합니다.
5. control 정본 승격 여부를 판단했습니다.
6. `state.md`와 `output.md`가 최신입니다.
7. 대시보드 재생성과 구문 검증이 통과했습니다.
