# MD 정본·HTML 대시보드 운영 방식 평가

기준일: 2026-08-13

## 1. 최종 평가

제안한 방식은 **8.5/10**으로 평가합니다. 소규모 사업 전략과 제품 기획을 장기간 유지하면서 사람과 AI가 함께 쓰기에 적합합니다.

단, 다음 조건이 지켜질 때의 점수입니다.

> Markdown만 정본으로 편집하고, HTML은 자동 생성하며, AI는 전체 문서 대신 짧은 현황 정본과 필요한 상세 문서만 선택적으로 읽는다.

| 평가축 | 점수 | 판단 |
|---|---:|---|
| 토큰 효율 | 9/10 | 전체 문서 재독 대신 점진적 로딩을 적용하면 큰 절감 가능 |
| 사람의 상황 파악 | 9/10 | 대시보드가 상태·위험·결정·지표를 빠르게 보여줌 |
| 지식 보존 | 9/10 | 버전 관리되는 MD와 결정 기록이 맥락 유실을 줄임 |
| 전략 품질 | 8/10 | 가설·증거·게이트를 함께 관리할 때 의견 중심 운영을 줄임 |
| 유지보수 | 7/10 | 자동 생성을 지키면 좋지만 수동 이중 편집 시 빠르게 붕괴 |
| 확장성 | 8/10 | 수십 개 문서까지 적합하며 이후 검색·DB로 확장 가능 |

## 2. 왜 효과적인가

### 단일 정본

GitLab의 handbook-first 방식은 새로운 해결책을 먼저 문서화하고 누구나 인정하는 한 개의 정본을 반복 갱신하는 구조를 강조합니다. [GitLab handbook-first](https://handbook.gitlab.com/handbook/company/culture/all-remote/handbook-first/)

이 프로젝트에서 Markdown은 다음 장점이 있습니다.

- Git 차이와 변경 이력이 남음
- 특정 문서만 선택해 읽을 수 있음
- 검색과 자동 변환이 쉬움
- 특정 SaaS나 브라우저에 종속되지 않음
- 다음 로컬 환경에서도 동일하게 사용 가능

### 짧은 현재 상태와 모듈형 상세 문서

Michael Nygard의 ADR 제안은 큰 문서는 읽히거나 갱신되기 어렵고, 작은 모듈형 문서가 결정 맥락을 유지할 가능성이 높다고 설명합니다. 결정이 바뀌면 이전 기록을 지우지 않고 대체 상태와 새 결정을 남기는 방식도 제안합니다. [Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

따라서 한 개의 거대한 사업계획서보다 `짧은 현재 상태 + 상세 주제 문서 + 결정 기록 + 검증 대장`이 적절합니다.

### 사람에게는 점진적 공개

PMI는 대시보드를 중요한 프로젝트 측정치에 대한 진행·성과를 보여주는 차트와 그래프의 집합으로 정의합니다. [PMI 프로젝트 관리 용어집](https://www.pmi.org/-/media/pmi/documents/registered/pdf/pmbok-standards/pmi-lexicon-pm-terms.pdf)

Nielsen Norman Group의 대시보드 사례도 첫 화면에서는 오류·경고·정상 같은 핵심 정보만 보여주고 선택할 때 세부 지표와 그래프를 펼치는 점진적 공개를 설명합니다. [NN/g Application Design Showcase](https://media.nngroup.com/media/reports/free/Application_Design_Showcase_1st_edition.pdf)

이 프로젝트의 HTML은 다음 순서로 보여줘야 합니다.

1. 현재 단계와 다음 게이트
2. 영역별 상태와 P0 위험
3. 90일 단계와 핵심 지표
4. 가설·결정·상세 문서

### AI에게는 선택적 컨텍스트

현재 Markdown 8개의 단순 파일 크기 환산치는 약 2.2만 토큰입니다. 모든 세션에서 이를 전부 다시 읽는 것은 불필요합니다. `../control/00_project_status.md`와 관련 상세 문서 1~2개만 읽는 방식이 실질적 절감 수단입니다.

TACL 2024의 `Lost in the Middle` 연구는 긴 컨텍스트에서 관련 정보의 위치에 따라 성능이 떨어질 수 있으며, 특히 중간에 있는 정보를 안정적으로 사용하지 못할 수 있음을 보였습니다. [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)

RAG 연구는 외부 지식을 전부 모델 내부나 한 프롬프트에 넣는 대신 관련 문서를 검색해 생성에 결합하는 접근을 제시합니다. 이 프로젝트는 대규모 벡터 검색까지 필요하지 않지만 `현황 정본에서 관련 상세 문서로 라우팅`하는 수동형 검색 구조를 같은 원리로 사용할 수 있습니다. [Retrieval-Augmented Generation](https://papers.neurips.cc/paper/2020/hash/6b493230205f780e1bc26945df7481e5-Abstract.html)

공식 OpenAI 문서도 반복 지침과 예시를 줄이고, 관련 도구만 노출하며, 세션이 길어질 때 컨텍스트 증가를 추적하라고 권합니다. 내부 코딩 에이전트 평가에서는 더 간결한 시스템 프롬프트가 토큰과 비용을 줄이면서 점수도 개선했지만 결과는 작업별 검증이 필요하다고 명시합니다. [OpenAI 모델 가이드](https://developers.openai.com/api/docs/guides/latest-model)

## 3. 사업 운영 관점의 보완

대시보드는 일정과 할 일만 보여주면 전략 도구가 되지 못합니다. 다음 네 축을 함께 봐야 합니다.

- 현재 고객 가치: 실제 유료 고객·반복 사용·리포트
- 잠재 가치: 검증되지 않은 고객 문제와 시장 기회
- 출시·학습 속도: 가설에서 증거까지 걸리는 시간
- 혁신 능력: 원가·기술 부채·API 한도·팀 공수

Scrum.org의 Evidence-Based Management도 Current Value, Unrealized Value, Time to Market, Ability to Innovate 네 관점으로 제품 가치를 검사하고 실험 결과에 따라 적응하도록 권합니다. [Evidence-Based Management](https://www.scrum.org/resources/evidence-based-management)

재무만 보면 선행 역량을 놓치기 때문에 Balanced Scorecard는 재무에 고객, 내부 프로세스, 학습·성장 관점을 보완합니다. [Kaplan·Norton Balanced Scorecard](https://hbr.org/2007/07/using-the-balanced-scorecard-as-a-strategic-management-system)

SaaS 단계에서는 획득, 참여, 유지, 성장, 경제성 지표를 구분해야 합니다. Stripe는 CAC, 회수기간, 리드 전환, 활성 사용자, churn·NRR, MRR·ARR, gross margin, LTV/CAC 등을 주요 범주로 제시합니다. [Stripe SaaS 지표](https://stripe.com/resources/more/essential-saas-metrics)

현재 마켓빅시는 매출 최적화 단계가 아니라 가설 검증 단계이므로 빈 MRR 차트를 만드는 것보다 유료 파일럿, 반복 사용, 원가 계측, 초안 게시율 같은 `측정 준비 상태`를 먼저 보여주는 것이 정직합니다.

## 4. 가장 큰 실패 조건

### HTML이 두 번째 정본이 되는 경우

HTML을 직접 고치면 다음 생성 때 변경이 사라지거나 MD와 충돌합니다. HTML 상단에 자동 생성·직접 편집 금지·생성 시각·소스 해시를 표시해야 합니다.

### 현황 요약이 상세 근거를 복제하는 경우

같은 가격·기능·전략 설명을 현황과 상세 문서에 모두 적으면 하나만 수정되어 모순이 생깁니다. 현황에는 짧은 결론과 정본 링크만 둡니다.

### 지표가 장식이 되는 경우

측정되지 않은 값을 0으로 표시하거나 근거 없는 건강도 점수를 만들면 잘못된 안정감을 줍니다. `미측정`, 측정 시작 조건, 통과 기준을 함께 표시해야 합니다.

### 기록 자체가 일이 되는 경우

모든 대화를 문서화하면 운영비가 커집니다. 바뀐 사실, 중요한 결정, 검증 증거, 다음 행동만 기록하고 일반적인 토론은 남기지 않습니다.

### 최신성이 사라지는 경우

대시보드가 보기 좋을수록 오래된 정보도 신뢰하게 됩니다. 마지막 갱신일과 14일 경과 경고를 표시하고, 투자 전에는 시장·법·API 자료를 재검증합니다.

## 5. 토큰 절감의 정확한 판단

효과가 있는 구조:

```text
사용자: HTML로 전체 현황 확인
AI: README + 00 현황 정본 읽기
질문 분류
관련 상세 MD 1~2개만 읽기
정본 갱신
HTML 재생성
```

효과가 없는 구조:

```text
AI가 HTML 전체 읽기
+ 모든 MD 전체 읽기
+ 대화 기록 전체 유지
+ 같은 사실을 여러 문서에서 갱신
```

따라서 이 방식은 `HTML 대시보드` 때문이 아니라 `정본 분리, 점진적 정보 공개, 선택적 문서 로딩, 결정·증거 기록` 때문에 효율적입니다.

## 6. 운영 권고

1. 새 세션은 항상 `README.md`와 `../control/00_project_status.md`로 시작합니다.
2. 상세 문서는 질문과 연결된 1~2개만 읽습니다.
3. 사용자 피드백은 먼저 사실·가설·결정·행동으로 분류합니다.
4. 사업 방향 변경은 결정 기록을 추가하고 과거 맥락을 삭제하지 않습니다.
5. 매주 현황을 갱신하되 실제 변화가 없는 표는 건드리지 않습니다.
6. 매월 가설 대장에서 통과·기각·수정 결정을 내립니다.
7. 문서가 수십 개를 넘고 검색 실패가 반복될 때만 색인·벡터 검색을 도입합니다.
