## 1차 비평 · 운영체계와 정본

판정: 구조는 사용할 수 있으나 현재 상태와 과거 업무 보고가 분리되지 않아 장기 운영 시 이력이 소실될 수 있다.

| 발견 | 개선 |
|---|---|
| 7개 역할은 초기 SaaS의 전략·고객·제품·판매·재무·기술·리스크를 대부분 포함 | 기존 7개 역할 유지 |
| 온보딩·지원·활성·갱신·이탈 책임이 SAL·PRD·TEC에 분산 | 고객성공 역할은 공백으로 유지하고 실제 고객 운영량이 생길 때 독립 여부 결정 |
| `state.md`·`output.md`는 최신값 덮어쓰기라 정기 상태 보고가 남지 않음 | 역할별 `updates.md`를 추가해 날짜별 결과를 누적 |
| `research.md`는 근거, `inbox.md`는 과업, 결정 로그는 방향 변경을 관리하므로 업무 업데이트와 목적이 다름 | 근거·과업·업데이트·결정을 각각 분리 유지 |
| 기존 6개 주제 화면은 역할 책임과 현재 업무를 바로 찾기 어려움 | D-015로 전체 현황+7개 역할 화면 채택 |

## 2차 비평 · 정보구조와 워딩

판정: 화면 구조는 사업 현황판에 가까워졌지만 계획·판단·성과·결정의 의미가 섞여 있었고, 담당·기한·완료일이 없어 실행 추적이 끊겼다.

| 발견 | 개선 |
|---|---|
| `output.md`의 계획·판단을 `최근 결과`로 표시해 실제 성과처럼 보임 | `현재 판단`으로 바꾸고 실제 완료는 과업 완료일과 `updates.md`에서만 표시 |
| 다음 행동·30일 계획·최근 업무가 같은 실행을 반복 | 전체 화면을 요약·KPI·역할·쟁점·실행·이력 6개 블록으로 축소 |
| `과거 단계`가 결정 기록을 대신하고 결정 대기 항목은 보이지 않음 | 완료 업무·사업 의사결정 이력·결정 대기를 분리 |
| 다음 행동에 담당 역할과 절대 기한이 없음 | 전사 실행과 역할 과업에 담당·목표일·완료일 필드 추가, 미확정 날짜는 `미정` 유지 |
| 현재 역할 상태와 과업·업데이트를 연결할 식별자가 없음 | `state.md`에 현재 과업 ID, `updates.md`에 과업 ID를 추가 |
| 협업 관계가 생성기에 하드코딩되어 등록부와 중복 | `personas/registry.md`를 역할 정의·입력·검토·산출물·전사 반영의 단일 정본으로 확장 |
| 대시보드 구조 결정이 최근 사업 결정을 가리고 대체된 결정이 진행 상태로 보임 | 결정에 사업·제품·시스템 범주를 추가하고 시스템 결정은 전체 화면에서 제외, 대체 상태는 중립 처리 |
| `3개 페르소나`, `source/persona/creative`, `UsageLedger`가 역할명·기술명과 혼동 | 고객 대상은 `3개 고객군`, 화면 용어는 `유입경로·고객군·소재`, `사용량 원장`으로 통일 |
| 761~980px에서 긴 표가 그대로 유지 | 980px부터 표를 세로 카드로 전환하고 480px부터 화면 기준일을 세로 배치 |

## 3차 비평 · 실제 운영성과 화면 검증

판정: 운영 구조와 화면은 통과했다. 실제 목표일·KPI·현금 데이터는 아직 입력 대기이며, 이를 완료값처럼 보이지 않고 전면 경고와 결정 대기로 관리한다.

| 발견 | 개선 |
|---|---|
| 실행 현황 표의 열 이름 차이로 사업 목표가 `미확인`으로 생성 | `항목·값`과 `항목·현재`를 모두 읽도록 파서를 수정하고 실제 사업 목표 출력 검증 |
| 완료된 STR-003·SAL-003·TEC-002가 현재 과업 ID에 남아 있음 | 현재 과업에서 제거하고 완료 업무·역할 업데이트 이력에만 유지 |
| 완료 업무가 실제 결과가 아니라 예정 산출물을 표시 | 과업 ID로 `updates.md`와 연결해 실제 결과를 표시 |
| 등록부와 역할 상태 파일이 같은 변동 상태를 중복 관리 | 등록부에서 상태 열을 제거하고 `state.md`만 상태 정본으로 사용 |
| 고객 온보딩·지원·갱신 공백이 안내문에만 존재 | Q-006 결정 대기와 STR-004 과업으로 등록 |
| 전사 실행 5건과 7개 역할의 목표일이 모두 미정 | 임의 날짜를 만들지 않고 상단에 미정 건수를 경고하며 Q-007 일정 확정 안건으로 등록 |
| 목표일 미정 집계값이 변수명 경계 오류로 빈칸 출력 | 집계 변수 경계를 명시하고 `전사 실행 5건 · 역할 7개` 출력 확인 |

## 최종 운영 판정

- 7개 역할은 현재의 초기 SaaS 검증 단계에 충분하다.
- 고객성공은 독립 역할로 늘리기 전에 SAL 주 담당, PRD·TEC 지원 또는 별도 담당 지정 중 하나를 Q-006에서 결정한다.
- 인사·법무 전담 역할은 현재 업무량에서 별도 화면으로 늘리지 않고 STR·RSK 책임으로 유지한다.
- 운영 시작 전 필수 입력은 Q-007의 절대 목표일, 실제 현금·원가, 유료·활성·획득 실측값이다.
- 화면 구조는 운영 가능하며, 현재 상태는 `일정·실측 데이터 입력 대기`다.

## 구현 후 3회 재검토

최종 판정: PASS. 남은 P0는 없다.

| 회차 | 판정 | 확인 |
|---:|---|---|
| 1. Git·정본·이력 | PASS | 중복 ID 즉시 실패, 명시 메타데이터 필수값·유형·역할·날짜 검증, 연결 ID 존재 검증 |
| 2. 정보구조·UI | PASS | 전체 현황+7개 역할, 상위 섹션 단일 열, 줄 수 제한 제거, 핵심 운영 정보 뒤 전체 자료 배치 |
| 3. 빌드·정적 조회 | PASS | 서버 요청 없이 카탈로그 로드, 모든 상세 화면의 원본 자료·해시 표시, 로컬 링크·JavaScript 검증 |

잔여 P1은 메타데이터가 없는 기존 문서가 경로 변경 시 새 ID를 받는 점과 카탈로그가 5,000건·10MB를 넘을 때 역할·유형별 분할이 필요한 점이다. 신규 독립 질문지·설계는 명시 메타데이터를 필수로 하고, 핵심 지표·리스크·예정 내역에는 고정 ID를 추가해 변동 범위를 줄였다.
