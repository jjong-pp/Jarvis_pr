## 프로젝트

### 1. 수요예측 대시보드 — 사내 운영 도구, 기획부터 배포까지 직접

사내에서 쓰는 운영 도구입니다. 외부 고객용 제품은 아니지만, 문제를 찾고 만들고 안 쓰이는 것을 확인해 고치는 사이클을 혼자 끝까지 돌린 유일한 건입니다.

**상황** — 40개 SKU의 수요·재고 판단을 매달 사람이 엑셀로 취합했습니다. 자료를 모으고 양식을 맞추는 데 매월 약 3~4일이 들었고, 품절이 임박한 품목을 미리 알아채지 못하는 일이 있었습니다.

**한 일**
- 요구사항 정리, 데이터 구조 설계, 구현, 배포까지 전 범위를 직접 수행 (생성형 AI 코딩 도구를 사용하고 도메인 규칙은 직접 검증)
- 최근 최대 12주 출고 평균과 출고–판매 차이 버퍼, 최신 현재고, 도착월이 있는 발주계획, 실무자 가중치로 **24주 예상 재고**를 계산하고 포장입수량 단위의 발주 제안량을 산출
- 품목 마스터 추가에 따라 SKU를 확장할 수 있는 구조로 설계

**안 쓰인 두 달** — 배포 후 두 달간 현업에서 쓰이지 않았습니다. 처음에는 기능이 부족한 줄 알았는데, 발주 검토 자리에 앉아 보니 문제가 다른 데 있었습니다. 실무자는 위험한 품목을 먼저 보고 원인을 확인한 뒤 수량을 정하는데, 제 화면은 전체 SKU와 숫자를 먼저 펼쳐놓는 순서였습니다. 정보는 다 있는데 순서가 달라 익숙한 엑셀이 더 빨랐던 겁니다.

사용자 옆에서 실제 발주 검토를 같이 돌려보며 화면 구성과 계산 로직을 함께 수정했습니다. 실무자가 감으로 조정하던 값은 없애지 않고 가중치로 넣을 수 있게 만들었습니다.

**결과** — 월간 발주 검토의 기준 자료로 안착했습니다. 매월 약 3~4일이 걸리던 취합·양식 업무를 대시보드 기반으로 전환했고, 전년도 12개월 재현 검증에서 2026년 5~6월 재고 부족 위험 4개 SKU를 식별했습니다.

`Python · FastAPI · SQLAlchemy · SQLite · pandas · openpyxl · HTML/CSS/JavaScript`

### 2. B2B 주문 시스템 — 수기 운영을 설정형 구조로

`2026.06 기획 → 07.02 개발 착수 → 07.16 핵심 서비스 전체 가동 → 08.31 최종 검수`
`계약처 약 140개소 · 공급사 5곳 · 커머스 솔루션 구축사 협업`

**문제 정의** — 30개소에서 굴러가던 구글 폼·시트·통장 대조가 140개소에서 무너졌습니다. 매일 입금 대조 15~30분, 월말 정산 2명 × 약 7시간, 오출고 월 2~3건. 주문 화면이 불편한 것이 문제가 아니라, 계약·결제·주문 상태를 사람이 매번 다시 판단하는 구조가 문제였습니다.

**판단** — 맞춤 개발과 타 솔루션 도입을 비교해 기존 커머스 솔루션에 정책을 얹는 쪽을 택했습니다. 결정 기준을 ① 운영팀 러닝커브 ② 기존 인프라 일치 ③ 유지보수 책임 범위 ④ 구축 비용 순으로 고정했습니다.

**뺀 것** — PG 결제는 B2B 마진 대비 수수료 부담이 커서 주 결제수단에서 제외했습니다. 견적서 신규 개발은 예산을 넘겨 기본 거래명세서로 대체했고, 포인트 완전 자동화는 계약 상태가 바뀔 때 지급이 번복될 위험이 있어 관리자 확인 단계를 남겼습니다.

**한 일** — 계약 예외를 코드가 아니라 `등급 × 카테고리` 관리자 설정값으로 분해해 새 계약이 생겨도 개발이 필요 없게 했습니다. 결제 방식이 다른 상품의 혼합 주문은 양방향 차단했습니다.

**결과** *(핵심 주문·입금·정산 흐름을 07-16 전체 가동해 관찰한 값입니다)*
- 오출고 **월 2~3건 → 0건** — 전체 측정 범위, 직전 6개월 월평균 대비 가동 후 약 1개월, 원천: 운영팀 출고·CS 이력
- 월말 정산 **2명 × 약 7시간 → 1명 × 30~60분** — 원천: 기존 수행자 확인
- 배송·주문·입금 문의 **2주 32건 → 19건** — 2026.01~06 인입의 2주 환산치 대비 배포 구간 2주 집계, 초기 관찰값

계약상 기본 개발요구 22건은 08-31 최종 검수를 기준으로 운영 QA를 이어갔고, 08-13 시점 17건이 운영 서버 확인 전 상태였습니다.

### 3. 리서치 SaaS 제품 재정의 — 가설마다 통과 기준을 먼저

`제품·사업 기획 (개발 구현은 동료 개발자 전담)`

동료와 함께 낸 아이디어에서 출발해 별도 서비스로 개설했고, 운영 중입니다. 네이버·유튜브·구글·인스타·뉴스의 조사 결과를 한 화면에 모으는 제품입니다.

**한 일**
- 조사가 업무인 직무 세 군을 **돈을 내는 상황** 기준으로 비교하고, 팔지 않을 대상 네 종을 먼저 명시
- 제품 흐름을 `워크스페이스 → SKU → 조사 브리프 → 근거 기반 초안 → 사람 승인 → 캠페인·추적 → 사용량·원가`로 재설계하고, 첫 범위에서 뺀 것 다섯 가지와 이유를 문서화
- **가설 14건에 각각 시험 방법·통과 기준·현재 증거·상태를 붙이고 증거를 A/B/C로 등급화.** 목표 미달 시 기각·수정·추가시험 중 하나로 판정하는 원칙을 명문화
- 실행 도중 **가설 하나를 폐기하고 다른 설계로 대체**했습니다. 채널을 순차 집행하려던 계획을 접고, 같은 페르소나·같은 제안을 두 채널에 동시에 걸어 비교하는 쪽으로 바꿨습니다. 폐기한 가설은 지우지 않고 상태를 '수정'으로 남겼습니다
- 유입부터 결제까지의 이벤트 정의안을 작성

**현재 상태** — 등록 사용자 약 20명이며 활성·유료·반복 사용 여부는 확인되지 않았습니다. 유료 검증은 기준을 정의한 단계까지 진행했습니다.

### 4. 통관 데이터 연동 — 흩어진 데이터의 책임을 나눔

`2026.02 ~ 2026.08`

주문 한 건의 데이터를 네 주체가 나눠 갖고 있어(자사몰·본인확인기관·해외 ERP·통관대행사) 어디도 신고 한 건을 혼자 완성할 수 없었습니다. 이 네 주체를 다섯 개 회사와 조율했습니다. 기능 요구가 아니라 데이터 소유권과 책임의 문제로 정의하고, 필드가 아니라 값의 의미를 고정하는 데이터 계약을 만들었습니다. 이 매핑표가 세 개발사의 개발 범위와 책임 경계를 정하는 기준 문서가 됐습니다.

운영 환경에서 30건을 검증해 테스트 목적 30/30을 통과했고(정상 접수 / 의도한 오류 반환 / 수정 후 재제출 성공), 리스크·질의 대장에 해결·기준확정 46건을 기록했습니다.
