## 프로젝트

### 1. 리서치 SaaS 제품 재정의 — 마켓빅시 BIGSEE

`2026 · 제품·사업 기획 및 운영 (개발 구현은 개발자가 전담)`

**상황** — 이미 공개돼 운영 중인 멀티채널 리서치 SaaS를 맡았습니다. 등록 사용자는 약 20명이었고, 그중 활성·유료·반복 사용 여부는 **확인되지 않은 상태**였습니다. 획득 경로 기록과 사용자당 원가도 측정되지 않았습니다.

**판단** — 기능을 늘리기 전에 *무엇을 모르는지*부터 확정해야 한다고 봤습니다. 제품이 답하지 못하는 질문을 목록으로 만들고, 확인된 사실 / 가설 / 미확인을 분리했습니다.

**한 일**
- 조사 결과가 다음 실행으로 이어지지 않는다는 문제를 정의하고, 사용자 여정에서 이탈이 발생하는 지점을 특정 — 기능 부족이 아니라 **보고서 작성 단계에서 서비스 밖으로 나가는 것**이 원인
- 조사가 업무인 직무를 조사 빈도·결정 권한·대체 수단 세 기준으로 좁혀, 광고대행사 실무자를 **1순위 검증 가설**로 설정 (확정 타깃 아님)
- 판매 MVP의 P0/P1/P2와 **제외 범위**를 확정하고, 각 단계를 통과해야 다음으로 넘어가는 검증 게이트를 정의
- AI 생성 결과의 품질 정책 설계 — 모든 조사값에 **출처·수집일·호출비용**을 기록하고, 출처가 없는 값은 초안 생성 입력으로 쓸 수 없게 차단. 확인되지 않은 값은 공백이 아니라 `UNKNOWN`으로 표기. 추정값·보정값은 표기 금지
- 생성물 게시 전 **금지 표현 자동 검사** 기준 정의 — 출처 없는 수치 / 효능·효과 단정 / 객관적 근거 없는 최상급 / 사용자 후기를 모방한 문장. 미통과 시 승인 단계로 진행 불가
- **사람 승인 없이는 캠페인·추적 링크를 만들 수 없도록** 권한을 설계하고(Owner·Admin만 승인), 승인자·승인 시각·초안 버전 이력을 남기도록 정의. 승인 후 수정하면 새 버전으로 저장하고 재승인
- 외부 API 호출량이 곧 직접 원가라는 점에 맞춰 이용 한도로 사용자 1인당 최대 원가를 고정하는 요금 구조를 설계

**산출물** — 제품 재정의 기획서 · 판매 MVP 요구사항 정의서 · 가설·검증 보드 · 서비스 프로세스 및 정책 정의서(회원·권한·요금·조사·결제·콘텐츠 승인 5개 영역)

**현재 상태** — 유료 파일럿·반복 사용·결제 검증은 **아직 실행 전**입니다. 측정 기준과 통과·중단 조건을 정의한 단계까지 진행했습니다.

> 리얼티쓰의 AI 자동 디자인도 결과를 전문가가 검토하고 승인해야 제조로 넘어갑니다. 위 경험은 **AI 결과의 근거·불확실성·승인 책임·버전 이력을 제품 규칙으로 고정한 사례**로 직접 이어집니다.

### 2. 관세청 전자상거래 통관 API 연동

`2026.02 ~ 2026.08 · 총괄 PM (정책·API 해석 / 요구사항·데이터 계약 정의 / 관계사 조율 / QA / 운영정책 수립) · 개발비 약 4,000만 원`

**상황** — 관세법 제254조 개정과 전자상거래 전용 통관플랫폼 도입에 따라, 자사몰 해외직구 주문의 거래정보를 수입 전에 제출해야 했습니다. 문제는 주문 한 건의 데이터가 **네 주체에 나뉘어 있었다**는 것입니다 — 자사몰(주문·결제·고객), 본인확인기관(개인통관고유부호 검증), 해외 ERP·WMS(상품·포장·운송장), 통관대행사(수입신고·병합).

**판단** — 신고 판단과 상태 통제의 중심을 해외 ERP가 아니라 **국내 DB로 옮겨야** 채널이 늘어도 견딘다고 봤습니다. 해외 ERP 중심·기존 Excel 유지·국내 DB 중심 세 안을 비교해 결정했습니다.

**한 일**
- 필드가 아니라 **값의 의미를 고정하는 데이터 계약**을 정의 — 고객 최종 결제액은 운송장별 신고가액과 분리해 관리, 원주문번호와 ERP 분할번호·운송장을 별도 식별자로 유지, 인증 정보는 해외 시스템에 전달하지 않고 국내에서 통관대행사로 직접 전달, 상품·실중량은 해외 ERP·WMS가 책임지고 자사몰은 재계산하지 않음
- 제출 단위 원칙 확정 — `운송장 1건 = 해외 포장 1건 = 제출 1건 = 통관 신고 1건`
- 정상 경로와 **오류 경로를 같은 비중으로** 설계 — 제출 → 오류코드 회신 → 관리자 화면에서 원인 확인 → 원천(자사/해외) 구분 후 수정 → 새 제출번호로 재제출. 처리창 안에 해결되지 않으면 자동 재제출·자동 출고를 막고 수동 통관으로 격리
- 운영 시각을 정책으로 분리 — 고객 주문 마감과 API 처리창을 별도로 두고, 미해결 건이 그대로 출고되지 않도록 차단
- **리스크·질의 대장**을 단일 정본으로 운영해 결정이 번복되면 이유와 날짜를 함께 기록. 오픈을 막는 항목(P0)과 오픈 전 정리 항목(P1)을 분리해 일정 판단의 근거로 사용
- API 필드 매핑표가 세 개발사의 개발 범위와 책임 경계를 정하는 기준 문서가 되도록 작성

**결과**
- 운영 환경에서 **30건 검증, 테스트 목적 30/30 통과** — 정상 건 접수 성공 / 의도 오류 건 예상 오류 반환 / 오류 수정 건 재제출 성공
- 대장 기준 **해결·기준 확정 46건**, 오픈 2일 전 시점 잔여 P0 4건 · P1 22건 · P2 7건을 부풀리지 않고 그대로 공개해 오픈 판정의 근거로 사용

**어려웠던 것** — 초기에는 관계사별 개별 협의로 전체 연동을 맞출 수 있다고 판단했습니다. 각 사가 자기 몫의 필드와 내부 로직만 공유하면서 데이터 소유권과 인터페이스 불일치가 뒤늦게 드러났고 **일정이 밀렸습니다.** 이후 E2E 흐름·필드 매핑표·책임 구분·리스크 대장을 하나로 통합하고 관계사 공동 검토로 전환했습니다. PM의 역할은 요구사항 수집이 아니라 **의존성과 실패 조건을 개발 전에 드러내는 일**이라는 것을 여기서 배웠습니다.

> 협력사는 실명 대신 역할(자사몰 개발사·ERP 개발사·물류개발사·통관대행사·본인확인기관)로 표기했으며 수치·계정 정보는 마스킹했습니다.

### 3. 산후조리원 전용 B2B 폐쇄몰 구축·운영

`2026.06 기획 → 07.02 개발 착수 → 07.16 핵심 서비스 전체 가동 → 08.06~08.13 운영 고도화·QA → 08.31 최종 검수`
`기획·정책 설계·SOW·외주 개발 조율·QA/UAT·운영 정책 설계 · 계약 조리원 약 140개소 · 공급사 5곳`

**상황** — 30개소에서는 굴러가던 구글 설문 주문·통장 대조·엑셀 정산이 140개소로 늘며 무너졌습니다. 매일 입금 대조에 15~30분, 월말 정산에 2명 × 약 7시간, 오출고가 월 2~3건 발생했습니다. 원인은 주문 화면의 불편이 아니라 **계약 조건이 담당자 기억에만 있어 시스템이 검증할 수 없다**는 것이었습니다.

**판단** — 가장 먼저 막을 것을 오출고와 입금 대조로 정했습니다. 맞춤형 웹서비스 직접 개발(유지보수 책임 부담)과 타 쇼핑몰 솔루션 도입(운영팀 러닝커브)을 비교해, **운영팀 러닝커브 → 기존 인프라 일치 → 유지보수 책임 범위 → 구축 비용** 순서로 판단해 기존 커머스 솔루션에 정책을 커스텀하는 안을 택했습니다.

**한 일**
- **계약 예외를 코드가 아니라 관리자 설정값으로 분해** — `회원등급 × 상품 카테고리` 표의 칸마다 노출 상품과 결제수단을 관리자가 선택하도록 설계. 새 계약 형태가 생겨도 개발 요청 없이 유형 추가만으로 대응
- 결제 방식이 다른 상품의 **혼합 주문을 양방향 차단**
- 입금 자동 매칭을 적용하고 미매칭 건만 수기 확인하도록 축소
- 하나의 주문 DB를 조리원 담당자·내부 운영팀·공급사가 **권한에 따라 다른 범위로** 보도록 정보 구조 설계. 공급사에는 배정 주문 조회·송장 입력을 열고 계약 단가·정산 정보·타 공급사 주문·고객 개인정보는 차단
- **범위에서 뺀 것과 이유를 문서로 남김** — PG 결제는 B2B 마진 대비 수수료 부담이 커서 제외, 별도 견적서 개발은 예산 초과로 기본 거래명세서로 대체, 포인트 완전 자동화는 계약 상태 변경 시 지급 번복 위험이 있어 `미리보기 → 대상 선택 → 재확인 → 실행`의 관리자 확인 단계를 유지
- 요청을 성격별로 분류하는 **ID 체계와 5종 고정 상태값**을 만들어 비용·일정 판단의 기준으로 사용. 완료 기준을 "운영 서버에서 기대 결과를 직접 확인했을 때"로 고정하고 배포 통보와 구분

**결과** *(핵심 주문·입금·정산 흐름을 2026-07-16 전체 가동해 약 1개월 관찰한 값이며, 계약상 기본 개발요구 22건은 08-31 최종 검수를 기준으로 운영 QA를 계속했습니다)*
- 오출고 **월 2~3건 → 0건** — 전체 측정 범위, 직전 6개월 월평균 대비. 원천: 운영팀 출고·CS 이력
- 월말 정산 **2명 × 약 7시간 → 1명 × 30~60분** — 원천: 기존 수행자인 경영관리팀·운영팀 확인
- 배송·주문·입금 문의 **2주 32건 → 19건** — 2026.01~06 CS 인입의 2주 환산치 대비 배포 구간 2주 집계. 품질·파손 등 서비스 밖 문의 비중은 오히려 증가

**배운 것** — 배포 후 추가한 기능 3개(월별 발주량 조회, 후불 주문 상태 분리, 거래명세서 다운로드 동선 단축)는 전부 기획서에 없던 것이고, 실제 업무를 보는 사람의 요청에서 나왔습니다. 다음에는 화면을 그리기 전에 하루를 따라가 보겠습니다.
