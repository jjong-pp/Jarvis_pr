## 1. 최종 결론

### 지원 우선순위

`선택적 스트레치 지원`이다. 지원 자체는 가능하지만 현재 세 문서를 그대로 제출하는 것은 권하지 않는다.

가장 큰 문제는 표현이 아니라 자격 게이트다.

- 공고 최소 경력: 2년
- 이력서 경력 시작: 2025.09
- 2026-08-26 기준: 12개월 미만

프로젝트 난도와 역할을 아무리 잘 설명해도 경력 2년 요건을 충족한 것으로 바꿀 수 없다. HR이 이를 하드게이트로 사용하면 포트폴리오가 열리기 전에 탈락한다.

경력 게이트를 예외적으로 완화해 상세검토를 받는다고 가정하면, 직무 준비도는 `50점 안팎`이다.

| 단계 | 모의 판정 | 핵심 이유 |
|---|---|---|
| 30초 HR 검토 | 탈락 가능성이 높음 | 최소 2년 경력과 문서상 1년 미만 경력이 정면 충돌 |
| 3분 상세검토 | 조건부 보류 | B2B 정책·QA·데이터·다자간 조율은 강하지만 PMF·리서치·로깅이 약함 |
| Product Lead 검토 | 스트레치 후보 | 운영·정책형 주니어 PM 증거는 있으나 성장형 E2E PM 증거 부족 |
| 사전과제 | 구조화·QA는 강점 | 고객 발견·지표·이벤트·AI 평가에서 감점 위험 |
| 면접 | 경력·역할·수치 검증이 핵심 | 경력 부족보다 역할 과장이나 증거 혼선이 더 치명적일 수 있음 |

공식 Factory 페이지는 다음 흐름을 제시한다.

```text
의뢰 접수
→ AI 디자인
→ 정밀 가공
→ 품질 검증
→ 출고·보증·고객지원
```

Factory까지 담당 범위에 포함된다면 웹 화면을 넘어 제조·품질·납기·고객지원까지 상태와 책임을 연결할 가능성이 있다. 다만 공개 페이지는 AI CAD와 Factory를 각각 설명할 뿐, 현재 두 서비스의 시스템·데이터 연동이나 이 채용 포지션의 담당 범위를 확인해 주지는 않는다. 면접에서 확인할 사안이다.

- [리얼티쓰 Factory](https://realteeth.ai/ko/factory)

### 회사 공개 수치는 정의를 분리해야 한다

공식 페이지에는 실제 케이스, 누적 의뢰, 학습 케이스, 처리량, 만족도, 효율 등 여러 수치가 나온다. 모두 회사 공개 또는 내부 분석 기반 값이며 외부 감사를 확인하지 못했다.

특히 다음은 서로 다른 모수일 수 있어 합치면 안 된다.

- 실제 사용 케이스
- 누적 의뢰 건수
- AI 학습 케이스
- 월평균 처리량
- SaaS 케이스와 Factory 제조 의뢰

지원 과제에서 이 수치를 그대로 성과로 인용하기보다 `정의·기간·분모·제품 범위가 무엇인가`를 먼저 질문하는 태도가 적합하다.

### 의료기기 여부는 미확인

공개 자료에서 REALTEETH SaaS의 식약처 의료기기 허가번호나 SaMD 지위를 확인하지 못했다. `ISO 12836/TC 106 기준 검증`도 제품 자체의 의료기기 허가를 의미하지 않는다.

지원서에서 다음 표현은 사용하지 않는다.

- 의료기기 인증을 받은 서비스
- 식약처 허가 AI 제품
- SaMD 규제 대응

안전한 표현:

> 환자 구강 스캔과 보철 제작 품질을 다루는 헬스케어 서비스이므로 데이터 동의, 품질 추적, 전문가 검토, 오류 복구가 중요한 제품이라고 판단했습니다.

임상 품질 기준과 법적 요구는 내부 도메인 전문가와 법무·규제 담당 확인이 필요하다.

## 3. 리얼티쓰 PM의 실질 요구

아래는 `공고에 직접 적힌 요구`와 `공개 제품을 바탕으로 한 지원자 가설`을 분리해 읽어야 한다. 특히 SaaS–Factory 연동과 현재 출시 단계는 미확인이다.

1. `[공고 직접]` 고객 문제 발견, 가설, 실험, PMF 학습을 주도하는 0→1 PM
2. `[공고 직접]` 웹·앱·어드민의 로드맵, 실행, 검증, QA 관리
3. `[공고 직접]` 제품 퍼널·핵심지표·로깅과 외부 브랜드 메시지 관리
4. `[지원자 가설]` 싱글 크라운에서 다른 보철 유형으로 확장하는 로드맵 관리
5. `[지원자 가설]` 치과기공사·치과 실무자의 전문 업무와 VOC 이해
6. `[지원자 가설]` 케이스 등록·업로드·AI 생성 이후의 전문가 검토·수정·승인·내보내기 흐름 설계
7. `[조건부 가설]` 담당 범위에 Factory가 포함될 경우 제작·검수·출고·고객지원의 상태와 데이터 연결
8. `[지원자 가설]` 제품 퍼널과 AI 품질 지표를 분리하고 품질 회귀·장애 복구 기준을 운영
9. `[지원자 가설]` 현재 무료 정책 이후의 과금·전환 실험
10. `[공고+가설]` 개발자·AI 연구자·디자이너·마케터·치의학 전문가 사이의 번역

이 역할은 요구사항을 받아 문서화하는 기획자보다 `발견-우선순위-실행-측정-학습`을 반복하는 제품 오너에 가깝다.

## 6. AI스러움 평가

이 회사의 AI는 LLM 챗봇이 아니라 3D 스캔, 형상 생성, 컴퓨터비전, 품질검증에 가까운 AI다. ChatGPT 사용량이나 프롬프트 개수보다 `불확실한 AI 결과를 전문 사용자가 검토하고 실제 제조에 연결할 수 있는가`가 중요하다.

현재 AI 네이티브성은 `8/15`다. 이는 `AI 문제·UX·책임을 설계하는 사고`의 점수를 포함한 것이며 AI 기능 직접 구현·운영 점수가 아니다. 현재 자료상 AI 직접 구현·운영과 평가·학습루프 증거는 낮다.

| 축 | 현재 | 판단 |
|---|---:|---|
| 문제-AI 적합성 | 2/3 | 조사 근거→해설·초안은 AI에 맞지만 치과 3D 문제의 직접 증거는 아님 |
| 입력·문맥·근거 설계 | 2/3 | 출처·수집일·선택 근거는 강함. 3D 입력 품질·모델 조건 경험 없음 |
| 인간-AI 통제 | 2/3 | `UNKNOWN`, 금지 표현, 사람 승인, 버전 이력은 전이 가능 |
| 평가·관찰 가능성 | 1/3 | 실제 평가셋·실패 로그·지연·비용·수정률 없음 |
| 운영·학습루프 | 1/3 | 승인·버전 정책은 있으나 사용자 수정이 모델 개선으로 연결되지 않음 |

판정:

> AI 제품의 책임과 통제를 설계하는 사고는 있으나, 3D·컴퓨터비전 AI를 측정·운영·개선한 증거는 없다.

### 리얼티쓰 지원을 위한 AI 네이티브 제안 흐름

```text
스캔 파일과 필수 조합 확인
→ 입력 품질·지원 유형 검증
→ AI 생성 조건과 처리 상태 표시
→ 결과·원본 비교
→ 전문가 수정·재생성·반려
→ 최종 승인·내보내기
→ 제조·품질검증 결과 연결
→ 수정·반려·재제작 사유 기록
→ 동의된 데이터만 모델 개선에 활용
→ 모델 버전별 회귀 검증
```

### AI 평가를 세 수준으로 나눈다

#### 모델 수준

- 입력 품질별 생성 성공률
- 생성 실패 유형
- 처리시간
- 모델 버전별 결과 차이
- 도메인 전문가 평가

#### 제품 수준

- 최초 승인 가능한 결과까지 걸린 시간
- 최초 결과 승인률
- 수동 수정 시간과 수정량
- 재생성·반려율
- 내보내기 성공률
- 첫 사례 완료율과 반복사용률

#### 사업·운영 수준

- 조직별 활성과 잔존
- 무료 베타→유료 전환
- 케이스당 지원 문의
- 제조 QA 통과와 재작업
- 고객지원·보증 비용

이 항목은 지원자의 제안 지표다. 리얼티쓰의 실제 내부 지표라고 표현하면 안 된다. 임상적 적합성 기준은 치과기공사·치과의사 등 도메인 전문가가 정의해야 한다.

## 7. 현재 자료의 강점

### 7.1 전문 업무를 시스템 정책으로 바꾼다

관세 프로젝트에서 법규·데이터 소유권·오류·재처리·감사 흐름을 구조화했다. 치과 경험은 아니지만 새로운 전문 도메인의 용어와 책임을 빠르게 제품 기준으로 바꾸는 전이 가능성을 보여준다.

### 7.2 웹·어드민·운영을 함께 본다

B2B몰은 사용자 화면만이 아니라 계정 유형, 권한, 결제, 포인트, 공급사, 정산, 운영자 정책을 함께 다룬다. 여러 사용자와 운영 상태를 연결하는 전이 가능성을 보여준다. 리얼티쓰에서 SaaS와 Factory를 함께 담당하는지는 미확인이므로 직접 적합 경험으로 단정하지 않는다.

### 7.3 실패·복구·QA 사고가 강하다

정상 흐름뿐 아니라 오류, 재제출, 상태 복구, 승인, UAT를 설계했다. 저품질 스캔·생성 실패·재작업이 가능한 AI 제조 흐름에서 유효한 강점이다.

### 7.4 기술 이해의 기반이 있다

API, 필드 소유권, idempotency, 데이터 상태, Python·MySQL 이해는 개발자·AI 연구자와 협업할 기반이 된다. 다만 SQL 분석이나 모델 평가를 실제로 했다는 뜻은 아니다.

### 7.5 AI 책임정책의 전이성이 있다

마켓빅시의 출처, 미확인값, 승인, 버전, 사용량 복원 정책은 AI 결과를 무조건 정답으로 취급하지 않는 사고를 보여준다.

## 10. 지원 전략

### 전략 A: 우선순위가 낮다면 보류

원더무브처럼 경력을 충족하고 직접 적합도가 높은 공고를 먼저 완성한다. 리얼티쓰는 사전과제와 3단계 면접이 있어 지원 비용이 높다. 경력 게이트를 넘을 가능성이 확인되지 않으면 주력 지원으로 두지 않는다.

### 전략 B: 스트레치 지원

먼저 채용 담당자 문의나 지원 메모를 통해 1년 미만 경력의 예외 검토 가능성을 확인한다. 회신을 받지 못하면 하드게이트 탈락 가능성이 높은 상태로 판단한다. 예외 검토 여지가 있을 때 다음 순서로 준비한다.

1. 사실 정합성을 수정한 2쪽 이력서
2. B2B몰 중심 E2E 타임라인과 실제 VOC·QA·운영 개선 증거
3. 실제 증거와 제안 가설을 분리한 이벤트 로깅·퍼널 1쪽
4. 리얼티쓰 공개 정보 기반 AI 검토·승인·학습루프 가설 2쪽

3~4번은 과거 수행물처럼 보이지 않도록 본문과 분리한 부록에 두고, 모든 페이지에 `공개 정보 기반 지원자 가설 / 미구현 / 실제 제품 상태 미확인`이라고 표시한다. 새 가설 문서는 실제 고객 발견 증거를 대체하지 않는다.

경력을 2년으로 부풀리지 않는다. 지원 메모를 쓸 수 있다면 다음처럼 정면으로 설명한다.

> 정규 경력 기간은 공고의 2년 요건에 미치지 않습니다. 다만 관세 API 연동과 B2B 주문 시스템에서 문제정의, 정책·데이터 설계, 개발 협업, QA, 출시 후 초기 운영까지 담당한 산출물을 기준으로 예외 검토를 요청드립니다.

`AI 자동화 구현 및 배포`는 실제 코드·화면·사용자·배포·전후 결과를 제시하거나 삭제한다.

## 13. 이벤트 로깅·퍼널 보강안

다음은 리얼티쓰의 실제 이벤트가 아니라 공개 제품 흐름을 기반으로 한 지원자 제안이다. `result_reviewed` 이후는 현재 공개 기능으로 확인되지 않았으며, 제조 이벤트는 SaaS와 Factory 데이터가 실제 연결되는 경우에만 적용한다.

### 핵심 이벤트

| 이벤트 | 의미 | 주요 속성 예시 |
|---|---|---|
| `case_created` | 새 케이스 등록 | 조직, 사용자 역할, 보철 유형 |
| `scan_upload_started` | 스캔 업로드 시작 | 파일 조합, 용량, 업로드 경로 |
| `scan_upload_completed` | 업로드 완료 | 소요시간, 파일 수 |
| `scan_validation_failed` | 입력 품질·형식 검증 실패 | 실패 코드, 누락 파일, 재업로드 여부 |
| `generation_started` | AI 처리 시작 | 모델 버전, 보철 유형 |
| `generation_succeeded` | 3D 결과 생성 | 처리시간, 모델 버전 |
| `generation_failed` | 생성 실패 | 오류 코드, 재시도 여부 |
| `result_reviewed` | 전문가가 결과 확인 | 첫 검토까지 시간 |
| `regeneration_requested` | 재생성 요청 | 반려·수정 사유 |
| `design_approved` | 전문가 승인 | 모델 버전, 승인 역할 |
| `design_rejected` | 전문가 반려 | 반려 사유, 입력·모델·사용성 구분 |
| `model_exported` | 결과 내보내기 | 형식, 성공·실패 |
| `manufacturing_qa_completed` | 제조 품질검증 | 통과·보정·재제작 여부 |
| `remake_requested` | 재제작 요청 | 사유, 최초 설계 버전 |

실제 로그에서는 환자 식별정보를 직접 속성으로 넣지 않고, 데이터 처리 기준은 내부 정책과 전문가 확인을 받아야 한다.

`manufacturing_qa_completed`, `remake_requested`는 조건부 확장 이벤트다. 실제 담당 제품 범위, Factory 연동, 데이터 식별자 연결 가능성을 먼저 확인해야 한다.

### 퍼널

```text
[SaaS 핵심 제안]
가입 조직
→ 첫 케이스 등록
→ 유효 스캔 업로드
→ AI 생성 성공
→ 전문가 검토·승인 가설
→ 내보내기 가설
→ 다음 케이스 반복사용
→ 유료 전환

[SaaS–Factory 연동 시 조건부 확장]
내보내기 또는 제작 의뢰
→ 제조 QA 통과
→ 재제작 여부
```

### 제안 핵심지표

북극성 지표 후보:

> 활성 기공소당 주간 `전문가 승인 완료` AI 디자인 케이스 수

지원지표:

- 첫 승인 케이스 완료율
- 첫 승인 결과까지 걸린 총 시간
- 스캔 재업로드율
- AI 생성 성공률
- 최초 결과 승인율
- 수동 수정 시간·수정량
- 재생성·반려율
- 내보내기 성공률
- 제조 QA 통과율
- 재제작률
- 조직별 주간 반복사용률
- 무료→유료 전환

북극성 지표와 모든 임계값은 실제 고객 인터뷰·운영 데이터·도메인 전문가 검토 후 확정해야 한다. 승인 케이스의 양만 늘리지 않도록 `전문가 수정시간`, `제조 QA 통과율`, `재제작률`을 필수 가드레일로 함께 둔다. 제조 지표는 실제 Factory 연동이 확인될 때만 사용한다.
