## 1. 이 포트폴리오의 목적

채용담당자가 문서를 모두 읽은 뒤 아래 한 문장을 믿게 만든다.

> 박종혁은 현장의 복잡한 문제를 사용자·정책·데이터 관점으로 구조화하고, 제한된 자원 안에서 우선순위를 정해 요구사항·QA·배포·운영 개선까지 연결한 주니어 PM이다.

프로젝트를 많이 수행했다는 인상을 주는 것이 목적이 아니다. 각 프로젝트를 통해 서로 다른 PM 역량을 증명한다.

- B2B 산후조리원 전용몰: 문제 정의, MVP 범위, 정책·권한, 출시, 운영지표 개선
- 관세청 연동: 규제 해석, 시스템·데이터 설계, 다자 조율, 오류 복구, E2E 검증
- BIGSEE: 기출시 제품 진단, 고객·가설 정의, 판매 MVP, 계측·검증 계획

## 4. 역량을 슬라이드에 표현하는 방식

별도의 추상적인 `나의 역량 10가지` 장을 만들지 않는다. 모든 역량은 아래 순서로 증명한다.

> 문제의 근거 → 판단 기준 → 선택·제외 → 직접 작성 산출물 → 협업·QA → 결과 → 다음 개선

각 프로젝트 표지에 역량 키워드를 최대 3개만 둔다.

- B2B: `MVP·정책 설계` / `출시·운영 개선` / `KPI`
- 관세청: `시스템·데이터 설계` / `이해관계자 조율` / `오류 복구·QA`
- BIGSEE: `제품 진단` / `가설·판매 MVP` / `계측·검증 설계`

슬라이드 제목은 주제명이 아니라 결론형 문장으로 작성한다.

- 나쁜 예: `MVP 설계`, `User Flow`, `성과`
- 좋은 예: `오출고와 입금 대조를 먼저 막고, PG·견적서·완전 자동화는 초기 범위에서 제외했습니다.`

## 5. MVP를 표현하는 정확한 기준

MVP는 작은 기능 묶음이 아니다. 특정 위험이나 가설을 가장 적은 비용으로 검증하는 최소 범위다. 모든 프로젝트에서 아래 다섯 질문에 답해야 한다.

1. 가장 먼저 줄여야 한 사용자·사업 위험은 무엇이었는가?
2. 어떤 데이터로 문제의 크기를 확인했는가?
3. 어떤 대안을 비교했고 무엇을 선택했는가?
4. 무엇을 초기 범위에서 제외했으며 왜 제외했는가?
5. 어떤 조건을 충족하면 출시·확장·중단하는가?

### B2B에서의 실제 MVP 증거

- 우선 위험: 반복 입금 대조, 월 오출고 2~3건, 월말 정산 2명×약 7시간
- P0: 계정별 상품 노출, 선불·후불 분기, 입금 자동 매칭, 혼합주문 차단, 주문·발주 DB화
- 제외·대체: PG 결제는 마진 영향으로 제외, 별도 견적서는 기본 거래명세서로 대체, 포인트 완전 자동 실행은 계약 변경 위험 때문에 관리자 확인 유지
- 출시 방식: 2026-07-16 핵심 서비스 전체 가동 후 운영팀·영업매니저의 실제 사용 피드백을 받아 2026-08-06~08-13 고도화·QA 반영
- 확장 근거: 발주량 조회, 후불 상태 분리, 거래명세서 접근성, 주문·배송 상태 가시성 등 운영 피드백 반영
- 설정형 확장성: `회원등급 × 상품 카테고리` 정책표에서 노출·결제수단을 관리자가 선택하고, 신규 등급·카테고리 추가 시 표가 자동 확장되도록 기획
- 되돌릴 수 없는 포인트 차감은 완전 자동화하지 않고 `미리보기 → 대상 선택 → 재확인 → 실행`으로 운영 통제

공급사 로그인 5개사, 주문 조회·다운로드·상태 변경·송장 입력 권한은 사용자 확정 사실이지만 현재 산후조리원 폴더에 계정 화면·권한표 증거가 없다. 실제 화면이나 권한표가 추가되기 전에는 본문 핵심 성과로 쓰지 말고 `추가 증거 삽입 예정`으로 표시한다.

### 관세청에서의 MVP 증거

- 목적은 기능 최소화보다 `법령·플랫폼 일정 안에 정상 제출과 오류 복구가 가능한 최소 안전 범위` 확정
- 정상 경로만이 아니라 본인확인 분기, 분할 출고, 미배정 차단, 오류 확인·수정·재제출을 오픈 필수로 설정
- 내부 산출물의 P0/P1 등급, 리스크·질의 대장, E2E 테스트를 우선순위 증거로 사용

### BIGSEE에서의 MVP 증거

- 제품은 이미 공개돼 있었으므로 `기획→출시`가 아니라 `인수 진단→고객·가치 가설→판매 MVP→유료 검증`으로 설명
- P0/P1/P2/제외 범위와 14일 파일럿 통과·중단 기준을 직접 작성한 산출물로 제시
- 실제 사용자·반복·결제·원가를 확인하기 전에는 개발 범위 가설로만 표기

## 6. 슬라이드별 추가·수정 지시

기존 22장 디자인 언어는 유지하되 프로젝트 순서를 `B2B → 관세청 → BIGSEE`로 재배치한다. 현재 PPT가 `관세청 → B2B → BIGSEE`이면 3~8장과 9~14장 블록을 통째로 교환하고, 상단 프로젝트 번호·목차·페이지 번호를 함께 동기화한다. 아래는 최종 수정 지침이다.

### 1장 — 자기소개

하단 강점 세 개를 추상 명사 대신 행동 문장으로 쓴다.

- 현장의 반복 오류와 담당자 의존을 사용자·정책·데이터 문제로 구조화
- 예산·마진·운영 위험을 기준으로 MVP와 제외 범위를 결정
- 요구사항·QA·배포 이후 지표와 피드백까지 연결

`데이터 드리븐`, `End-to-End`, `PMF` 같은 단어만 단독으로 쓰지 않는다.

### 2장 — 프로젝트 목차 겸 PM 역량 지도

프로젝트 카드 아래에 아래 한 줄씩 추가한다.

- B2B: `문제 근거 → MVP 범위 → 정책·권한 → 단계 배포 → 운영지표`
- 관세청: `법·규격 해석 → 데이터 책임 → E2E·오류 복구 → 테스트`
- BIGSEE: `인수 진단 → 고객 가설 → 판매 MVP → 계측·유료 검증 계획`

우측 또는 하단에는 3×3 역량 매트릭스를 작게 배치한다. 체크 표시는 해당 프로젝트의 실제 산출물이 있는 역량에만 사용한다.

| 역량 | B2B | 관세청 | BIGSEE |
|---|:---:|:---:|:---:|
| 문제 정의 | ● | ● | ● |
| MVP·우선순위 | ● | ● | 계획 |
| 정책·요구사항 | ● | ● | ● |
| 데이터·기술 | ● | ● | 설계 |
| QA·출시 | ● | 운영 환경 검증 | 미실행 |
| 운영성과·검증 | ● | 테스트 목적 30/30 | 검증 예정 |

### 3~8장 — B2B 산후조리원 전용몰

이 프로젝트가 가장 완성된 PM 사례다. 기능이 많다는 것이 아니라 문제·선택·배포·결과가 닫혀 있다는 점을 보여준다.

- 3장: 프로젝트 표지·수행 요약. `2026.06 기획 → 2026.07.02 개발 착수 → 2026.07.16 핵심 서비스 전체 가동 → 2026.08.06~08.13 운영 고도화·QA → 2026.08 성과 집계`. 역할은 `서비스 기획·정책 설계·SOW·외부 개발사 협업·QA·운영 반영`으로 표기
- 4장: 30여 개소에서 유효했던 구글 설문·Excel·통장 대조가 140여 개소로 늘며 무너진 이유. AS-IS를 `주문 접수 → 거래명세서 메일 → 입금 대조 → ERP 등록 → 출고 → 월말 정산`으로 그리고, 문제를 `담당자 기억·반복 확인·예외 계약·데이터 단절` 네 가지로 묶기
- 5장: 맞춤형 웹서비스·타 쇼핑몰·고도몰5를 비교해 기존 자사몰 인프라와 운영팀 러닝커브 때문에 고도몰5를 선택한 판단. P0와 제외 범위를 같은 화면에서 대비
- 6장: `등급 × 카테고리 × 결제방식` 정책 매트릭스. 사용자 명칭은 `분유 선불 / 분유 후불 / 물품 선불 / 물품 후불`, 실제 시스템 명칭은 각주로 `선불입금 / 후불입금 / 물품계약(선불) / 물품계약(후불)` 표기. 카테고리는 분유·물품·미지정, 결제방식은 무통장·포인트·후불 발주로 표현
- 7장: 조리원 담당자·운영팀·경영관리팀·영업매니저의 역할별 흐름. `계약 조건 전달 → 계정·정책 설정 → 상품 노출 → 주문·입금 → 주문상태·배송 확인 → 거래명세서 → 월말 포인트 정리·정산`을 하나의 서비스 여정으로 연결
- 8장: 07.16 전체 가동 후 08.06~08.13 고도화·QA, 운영 성과, 다음 개선을 한 장에서 닫기. 숫자마다 측정 기간·모수·원천·상태를 각주로 표기

5장의 제목 권고:

> 오출고와 입금 대조를 먼저 막고, 비용·마진·운영 위험이 큰 기능은 초기 범위에서 제외했습니다.

8장 하단에는 배포 후 추가한 기능 3개만 보여준다.

- 월별 발주량 조회
- 후불 주문 상태 분리
- 거래명세서 다운로드 동선 단축

### 9~14장 — 관세청 연동

이 프로젝트는 `법이 바뀌어서 API를 붙였다`가 아니라 `규제·본인확인·주문·물류·통관의 책임과 오류 복구 흐름을 설계했다`로 보여준다.

#### 사실 정정

- 금지: `2026년 8월 시행 관세법 개정`
- 권장 제목: `관세법 제254조 개정 및 전자상거래 전용 통관플랫폼 도입 대응`
- 법령 개정 공포: 2024-12-31
- 관세법 제254조·시행령 제258조 개정규정 시행: 2026-01-01
- 전용 통관플랫폼 시범운영: 2026-08-28
- 정식 개통: 안정화 후 2026년 내 예정

법은 관세청장이 필요한 경우 등록 사업자에게 수입 전 거래정보 제공을 요청할 수 있다고 규정한다. `모든 사업자의 모든 거래 자동 제출 의무`라고 단정하지 않는다.

9장 한 줄 설명 권고:

> 자사몰·외부 채널의 주문·결제 정보를 국내 DB에서 표준화하고, 관세청 요청 시 수입 전 전송과 오류 수정·재제출이 가능하도록 전사 흐름을 기획했습니다.

- 9장: 법령·플랫폼 도입 배경, 기간, 역할, 예산, 4개 데이터 영역과 5개 관계사 구분
- 10장: 해외 ERP·몰·본인확인·특송/통관에 데이터가 나뉘어 있는 문제와 국내 DB 중심 통제 필요성
- 11장: 해외 ERP 중심·Excel 유지·국내 DB 중심 대안 비교와 RACI
- 12장: `PCCC·OTP 본인확인 → 결제 → ERP 주문수집 → HBL 대기·대사 → TRA001 제출 → TRA003 오류 판정 → 정상 출고 또는 실패 격리` E2E. 정상 경로와 오류 경로를 같은 그림에서 분기
- 13장: 고객 주문 마감 정책과 API 자동 처리창을 분리해 표기. `고객 주문 마감 09:00`과 `HBL·TRA 처리 11:10 시작 → 11:50 마감`을 혼동하지 않기. 11:50까지 정상 근거가 없으면 `MANUAL_CLEARANCE_REQUIRED`로 격리하고 자동 재제출·자동 출고를 금지
- 14장: 운영 환경 검증 30건의 설계 범위와 결과. `오류 코드 약 1분 내 회신 → 원천 확인 → 값 수정 → 새 제출번호로 재제출`은 처리창 내 수정 건으로 표시하고, 마감 이후 무한 자동 루프처럼 그리지 않기

#### 관세청 12장 오류 루프의 정확한 표현

```text
정상 데이터 → TRA001 접수 → TRA003 정상 확인 → 출고 허용
의도 오류/실오류 → TRA003 오류코드·원문 적재 → 실패 목록 노출
  ├─ 처리창 내 수정 가능: 원천값 수정 → 새 제출번호 채번 → 재제출 → 결과 재확인
  └─ 11:50까지 미해결: 수동 통관 목록 격리 → 자동 재제출·출고 차단 → 운영자 승인 후 해제
```

오래된 발표자료의 `09:00 수집`, `p1 원복 후 익일 무제한 자동 재처리`, `실사용 가능한 PATCH 수정 API`는 현재 정본이 아니므로 삭제한다.

#### 관세청 14장 검증 시나리오 6개 군

| 검증 군 | 기획서 근거 | PPT 표현 |
|---|---|---|
| 업체·운영 부호 | OAuth 주체, 제출업체 부호, 제출번호 앞 9자리, 판매자·구매대행자·판매중개자 부호 분리 | `부호 의미가 다른 필드를 하나의 코드로 오인하지 않도록 검증` |
| 직구·내수 혼재 | `isCrossBorder`와 `elcm_pcd` 분리, 직구 신고 실패 시 원주문 단위 삭제·내수 동반 지연 정책 | `시스템의 최소 처리 단위를 정책으로 보완` |
| 다중·분할 HBL | 전 HBL 확정 전 제출 차단, 1 HBL=1 포장=1 TRA001=1 HWB | `누락 운송장이 있으면 전체 대기` |
| 본인인증 분기 | PCCC·OTP 정상/불일치, 변경 시 재검증 | `결제 단계에서 오류를 앞단 차단` |
| 의도 오류값 | 중복 제출 3000, PCCC·우편번호 오류 3180, 판매업체 필수값 누락 등 | `예상 오류를 정확히 반환·분류` |
| 수정·재제출 | 오류 확인, 원천 수정, 새 제출번호, 재제출, 마감 이후 수동 통관 | `실패를 발견하는 데서 끝내지 않고 복구 경로까지 검증` |

성과 문구는 아래를 그대로 사용한다.

> `운영 환경 30건 테스트 목적 30/30 통과`  
> 정상 건 접수 성공 · 의도 오류 건 예상 오류 반환 · 수정 건 재제출 성공

`30건 모두 정상 신고 성공`이라고만 쓰지 않는다. 의도 오류 건과 논리적으로 충돌한다. 30건을 여섯 시나리오에 몇 건씩 배분했는지는 로그가 없으므로 비율을 만들지 않는다.

#### 관세청에 반드시 추가할 증거 자리

- `[실제 화면 삽입] TRA001 제출 현황 목록` — 주문번호·PCCC·HBL·제출번호 마스킹
- `[실제 화면 삽입] TRA003 의도 오류 응답` — 오류코드와 오류 필드만 남김
- `[실제 화면 삽입] 동일 주문 수정 전/후` — 어떤 원천값을 고쳤는지 콜아웃
