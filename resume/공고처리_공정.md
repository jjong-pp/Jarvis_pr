# 공고 처리 공정

Claude Code와 GPT(Codex)가 함께 쓰는 공정 정본이다. 경력 사실은 [공통자료/SCM_업무성과.md](공통자료/SCM_업무성과.md)와 [공통자료/PM_프로젝트성과.md](공통자료/PM_프로젝트성과.md), 지원 선호는 [AGENTS.md](AGENTS.md)를 따른다. 평가자 지시는 [평가_역할카드.md](평가_역할카드.md)에 있다. 이 파일은 순서·게이트·파일 규칙만 정한다.

## 1. 모드

토큰이 기본값이고, 사용자가 `정밀` 또는 `울트라`라고 말한 공고에만 성능 쪽으로 바꾼다.

| 항목 | 기본 (토큰 우선) | 정밀 (지시할 때만) |
|---|---|---|
| 공고 분석 | 메인 에이전트가 원문·기존 정본 중심으로 작성, 판단을 바꿀 외부 사실만 최소 확인 | 회사·제품 외부 조사 추가 |
| 평가 3종 입력 | 공고 원문 + 기본틀 + 이미 있는 공고 전용 문안 | 사실 원장 해당 절 전체 추가 |
| 평가 모델 | Claude: sonnet / GPT: 기본 모델 | 최상위 모델 |
| 재검 | 평가 C 1회 | 평가 3종 재실행 |
| 산출물 | 이력서 MD, PM이면 포트폴리오 계획 | 동일. 자기소개서는 공고가 요구할 때만 |

[2026-10-07 정정] 종전 기본 모드의 `공고 원문만` → 회사·제품의 포괄 조사는 생략하되, 공고 상태·필수 자격 등 판단을 바꾸는 최신 정보나 핵심 근거 공백, 사용자의 조사 요청은 범위를 한정해 1차 자료를 확인한다. 외부 조사의 위임은 `AGENTS.md`의 공통 실행 원칙을 따른다.

## 2. 폴더와 파일

새 공고는 `{PM용|SCM용}/{회사}_{직무}_{공고ID 또는 식별명}/`에 둔다. 대분류가 애매하면 사용자에게 한 번 묻는다.

| 파일 | 단계 | 내용 |
|---|---|---|
| `공고원문.txt` | S0 | 사용자가 준 원문 그대로 |
| `jd_snapshot.md` | S0 | 확인일·URL·상태·마감·제출서류, 필수·우대 요약 |
| `공고분석.md` | S1 | 자격 게이트, 필수·우대·업무, 이 공고가 실제로 찾는 사람, 트랙(L/P) |
| `적합도_3관점.md` | S3 | 평가 3종 종합, 공통 결론, 이견, 판정, 반영 내역 |
| `이력서.md` | S4 | 제출용 전문. 맨 위에 기본틀 대비 변경 3~5줄 |
| `포트폴리오_수정계획.md` | S4 | PM만. 기본틀 슬라이드 번호 기준 유지·이동·교체·삭제 |
| `교차검증_{엔진}.md` | 선택 | 다른 엔진이 같은 공고를 다시 평가한 기록 |

기본틀은 대분류 바로 아래 `기본틀_*` 파일이다. 공고 폴더에서 기본틀을 덮어쓰지 않는다. 공고 세 건 이상에서 같은 수정이 반복되면 기본틀 개정을 사용자에게 제안한다.

## 3. 루프

```text
S0 입수    원문 저장 → jd_snapshot → 지원현황.md에 행 추가 (상태: 분석)
S1 분석    공고분석.md. 공고가 필수라고 쓴 것만 게이트로 본다. 미확인을 미충족으로 바꾸지 않는다
S2 평가    `평가_역할카드.md`의 A·B·C를 서로 독립으로 실행 (병렬 가능, 서로의 결과·공고분석.md를 읽지 않음)
S3 종합    적합도_3관점.md → 판정 지원/조건부/보류 (상태: 결정대기)
           ── 사용자 결정 게이트: 지원 여부, 결과를 바꾸는 사실 질문 1~3개 ──
S4 작성    이력서.md, (PM) 포트폴리오_수정계획.md (상태: 작성)
S5 재검    평가 C가 S4 산출물만 다시 본다 → READY / REVISE(재작업 1회) / BLOCK(사용자 보고) (상태: 검증)
S6 기록    지원현황.md 갱신 (상태: 제출대기). 제출은 사용자가 한다
S7 회고    서류 결과가 나오면 지원현황.md에 결과·추정 사유 1줄. 같은 사유가 2회면 기본틀·지원방향 개정 제안
```

- REVISE 재작업은 1회뿐이다. 두 번째에도 READY가 아니면 멈추고 쟁점만 보고한다.
- BLOCK은 사실 문제다. 작성으로 해결하지 않고 사용자에게 올린다.
- 사용자가 `분석만`이라고 하면 S3에서 멈춘다. `바로 작성`이라고 하면 결정 게이트를 건너뛴다.

## 4. 종합 규칙 (S3)

- 판정은 다수결로 정한다. 셋이 모두 다르면 가장 보수적인 판정을 채택하고 이견을 적는다.
- 같은 축의 점수 차가 2점 이상이면 `쟁점`으로 표시하고 양쪽 근거를 함께 남긴다. 평균으로 덮지 않는다.
- 하드 게이트가 `미확인`이면 판정은 최대 `조건부`다. `미충족`이면 `보류` 또는 `스트레치`로 표시한다.
- 합격 확률 숫자는 쓰지 않는다.

## 5. 작성 규칙 (S4)

- 이력서 섹션 순서는 기본틀을 따른다: 간략 소개 → 이력(경력·학력·수상·활용 역량) → 경력 및 프로젝트 → 자기소개와 일하는 방향 → 성공과 실패 경험.
- 바꾸는 것은 프로젝트 순서, 강조 문장, 뺄 소재다. 새 사실·수치를 만들지 않는다.
- 연락처는 쓰지 않는다. 사용자가 양식에 직접 넣는다.
- 포트폴리오는 [공통자료/포트폴리오_베이스.md](공통자료/포트폴리오_베이스.md)의 슬라이드 번호로 계획한다.
- PPTX는 사용자가 `PPT 반영`이라고 지시할 때만 한 번에 만든다.
  - 기본틀 복사본의 텍스트만 교체하고 레이아웃은 바꾸지 않는다.
  - 저장 위치는 공고 폴더이고, PDF는 만들지 않는다.
  - 검사는 파일 무결성과 텍스트 넘침만 한다. 제출 전 PowerPoint 열기 확인은 사용자에게 권한다.

## 6. 엔진 간 인계

- 상태는 대화가 아니라 [지원현황.md](지원현황.md)의 상태값과 공고 폴더 파일로 넘긴다.
- 작업을 시작할 때 해당 행의 `작업중` 칸에 `엔진 시각`을 적고, 끝나면 비운다. 다른 엔진이 작업 중인 공고 폴더의 파일은 고치지 않는다.
- 작성한 엔진과 재검하는 엔진을 다르게 두는 것을 권장한다. 자기가 쓴 문서를 자기가 검증하면 놓친다.
- Claude는 `.claude/agents/fit-eval-*` 3개를 병렬로 호출한다.
- GPT는 역할카드를 하나씩 실행하되, 각 평가를 시작하기 전 이전 평가 출력을 참조하지 않는다. 가능하면 별도 스레드에서 실행한다.

## 7. 사실 출처

## 8. 전 단계 공통 금지

- 정식 사용자 인터뷰, 사용성 테스트, A/B 테스트, 이벤트 로깅 구현·운영을 경험으로 쓰지 않는다.
- Figma·Notion·Jira 숙련을 쓰지 않는다.
- 마켓빅시(BIGSEE)의 PMF·유료 전환·리텐션 검증, 본인 직접 개발을 쓰지 않는다. 시작월은 쓰지 않는다.
- 공급사 수·단가·마진을 공개하지 않는다.
- 비교 범위가 확인되지 않은 정산 시간 단축 수치를 쓰지 않는다.
- 테스트 통과를 운영 성과로, 계획을 완료형으로, 개발사 구현을 본인 개발로 쓰지 않는다.
- 수치에는 기간·모수·측정 상태를 붙인다.
