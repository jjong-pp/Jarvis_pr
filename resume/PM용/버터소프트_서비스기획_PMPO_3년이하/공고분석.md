## 이 공고가 실제로 찾는 사람 (추론)

1. 전략만 제안하는 PO보다 요구사항을 기능·정책·IA·화면 흐름으로 바꾸고 구현·검수까지 닫는 실행형 서비스 기획자.
2. 앱·웹·키오스크와 백오피스 사이의 상태·권한·결제·예외를 빠뜨리지 않고 운영 기준으로 문서화할 사람.
3. 자사 서비스와 고객 프로젝트를 오가며 디자이너·프론트·백엔드·이해관계자의 언어를 연결하고 일정을 맞출 사람.
4. 완성된 분석 체계가 없는 초기 환경에서도 CS·오류·운영 데이터로 개선 후보를 정리할 사람.

## 지원 내용 세팅

### 핵심 포지셔닝

`B2B·백오피스의 운영 규칙을 정책과 화면·데이터 흐름으로 구체화하고, 개발 협업과 QA를 거쳐 운영 전환한 서비스 기획자`

공식 직함은 숨기지 않는다. `아이베 SCM팀 사원 / 프로젝트 PM(기획·요건 정의·관계사 조율·QA·운영 전환)`으로 소속과 역할을 함께 쓴다.

### 이력서 배치

1. **B2B 주문몰:** 관리자 결제 설정, 4개 계정 유형의 권한, 혼합주문 차단, 포인트 정리 안전장치, 운영 서버 QA를 전면 배치한다.
2. **신규 ERP 주문·물류 연계:** 주문·상품·WMS·통관 API 요건과 약 100건 테스트로 백오피스·검수 증거를 보강한다.
3. **관세청 연동:** 상태·필드·예외·재제출 기준과 다자 조율을 Flow·정책서 대응 근거로 쓴다.
4. `사용자 중심`은 정식 인터뷰로 확대하지 않는다. `영업담당자 CS 회의 + 주간 보고서 3주 관찰 → 문의 유형 분류 → 거래명세서·배송 정보 기능 반영`으로 쓴다.
5. 모바일·키오스크 경험, IA·Wireframe 산출물, Figma·Notion은 확인 전 추가하지 않는다.

### 포트폴리오 배치

- 1순위 B2B(현재 p3~10): p5 대안, p6 관리자 정책, p7 예외, p8 안전장치, p9 QA, p10 결과를 공고 핵심과 직접 연결한다.
- 2순위 관세청(현재 p18~23): p20 구조, p21 결정, p22 상태, p23 검증으로 Flow·다자 협업·예외 복구를 증명한다.
- 3순위 마켓빅시(현재 p11~17): 고객군·정책 설계는 보조로 축소하고 유료 전환·리텐션 결과처럼 쓰지 않는다.
- PPTX는 `PPT 반영` 지시 전 수정하지 않는다. 제출 전 p3의 공급사 수는 일반화하고, p10 정산 개선·측정 기간을 최신 정본으로 반영한다.

## 예상 탈락 사유

1. **상:** 공식 직함이 SCM팀 사원이어서 첫 화면에서 PM 경력이 약하게 읽힐 수 있다.
2. **상:** IA·Wireframe과 소비자용 모바일·키오스크 UX의 직접 증거가 없다.
3. **중:** 사내 디자이너·프론트·백엔드 스쿼드 및 Figma·Notion 사용 경험이 확인되지 않았다.
4. **중:** 데이터 기반 개선 증거는 있으나 정식 사용자 인터뷰·사용성 테스트·제품 행동지표 운영 경험은 없다.
