이 폴더의 목적은 공고 지원을 위한 이력서·자기소개서·포트폴리오 작성, 공고 맞춤 적합도 분석, 지원 전략 수립이다. 새 대화에서도 기존 판단을 이어가며 이미 확정한 사실을 다시 묻거나 처음부터 재조사하지 않는다.

## 공고 한 건 처리

절차의 정본은 `공고처리_공정.md`다. 요약: 원문 보존 → 공고 분석 → 독립 평가 3종(채용 의도 / 증거 적합도 / 탈락 위험) → 종합 판정 → 사용자 결정 → 공고 전용 이력서·포트폴리오 계획 → 다른 관점의 재검 1회 → `지원현황.md` 기록. 기본은 토큰 우선 모드이고, 사용자가 `정밀`·`울트라`라고 할 때만 성능 모드로 바꾼다.

합격 가능성은 근거 없는 단일 백분율로 말하지 않는다. `지원 권고/조건부/보류`, 자격 게이트, 증거 강도, 핵심 공백과 예상 탈락 사유로 설명한다.

## 사용자 질문 규칙

- 한 번에 1~3개만 묻고, 지원 판단이나 문안이 실제로 달라지는 질문부터 묻는다.
- 각 질문에 `왜 필요한지`와 `가능하면 받을 증거`를 짧게 붙인다.
- 반복 관리가 필요한 질문은 `Q-FACT / Q-EVIDENCE / Q-PREF / Q-JD` ID와 `OPEN / ANSWERED / DEFERRED` 상태를 붙인다.
- 이미 답한 내용은 다시 묻지 않는다. 날짜·수치·역할이 충돌하거나 기준 시점이 바뀐 경우에만 재확인한다.
- 답은 후보자 사실, 증거 범위, 장기 선호, 특정 공고 선택 중 하나로 분류해 해당 정본에 반영한다.
- 낮은 영향의 미확인 항목 때문에 초안 작성을 멈추지 않는다. `CONFLICT` claim은 항상 제외하고, 그 claim이 공고의 핵심 근거라면 작성을 차단한다.

## 문서별 책임

- 간략 소개: 지원 방향과 문제 해결 방식. 프로젝트 성과를 반복 나열하지 않음
- 이력서·경력기술서: 기간·역할·범위·검증 가능한 결과 중심
- 자기소개서: 지원동기와 공고에 가장 가까운 사례를 구체적 장면으로 설명
- 포트폴리오: 문제 근거 → 판단·대안·제외 → 정책·요구사항·흐름 → QA·배포 → 결과·한계
- 지원 전략: 왜 지원할지, 무엇을 앞세울지, 어떤 공백을 인정하고 보완할지 결정

핵심 메시지는 공유하되 문장을 그대로 복사하지 않는다. 제품·0→1·AI 공고는 BIGSEE, 커머스·운영 PM은 B2B몰, 규제·SI·연동은 관세청을 우선 배치한다. 광범위한 주니어 PM 공고는 완결된 실행과 측정이 있는 B2B몰을 기본 첫 사례로 둔다.

## 작성·검증 기준

- 한국어로 건조하고 구체적으로 작성. 불필요한 영한 병기와 방법론 이름 나열 금지
- `A가 아니라 B`, 추상명사 병렬, 과도하게 매끈한 성공 서사 등 AI 초안 문체 제거
- 숫자에는 기간·모수·비교 기준·원천·측정 상태를 가능한 범위까지 붙임
- 본인 역할과 개발자·디자이너·현업·외부사의 역할을 분리
- 기능·성과를 `운영 중 / 구현 완료 / 테스트 완료 / 정책 설계 / 제안 / 미계측`으로 구분
- 실제 화면, 재구성 화면, 계획 화면을 라벨로 구분하고 개인정보·단가·주문번호 마스킹
- 제출 전 이력서·자소서·포트폴리오의 회사명·직무명·기간·수치·역할·링크를 교차 대조
- 정본을 고친 뒤 `resume/` 전체에서 종전 값을 검색하고, 영향을 받은 기존 지원본은 수정하거나 `STALE`로 표시
- 외부 제출·지원·담당자 연락은 사용자의 최종 승인 전 실행하지 않음

## 이전현황 유지 (사용자 요청 시)

[2026-10-03 사용자 지시] 사용자가 이전현황 정리, 커밋 준비, 현재 상황 기록을 요청할 때마다 아래를 수행한다. 요청이 없으면 하지 않는다.

1. `git status`로 미커밋 변경과 새 파일을 모두 확인한다. 다른 엔진의 변경도 빠짐없이 적고 작성 엔진을 구분한다
2. `지원현황.md`의 `작업중` 칸을 확인한다. 다른 엔진이 작업 중인 공고는 상태만 적고 그 폴더는 고치지 않는다
3. `이전현황.md`의 `현재` 절을 덮어써 갱신한다. 절 구성은 `진행 중 / 이번 작업에서 바뀐 것 / 대화에서만 나온 판단 요약 / 사용자 결정 대기(질문 ID) / 열린 문제 / 커밋 전 확인`이다
   - [2026-10-04 보완] 덮어쓰기 직전에 파일을 다시 읽고, 기존 `현재` 절 전체를 `이전현황_기록.md` 맨 아래에 `## YYYY-MM-DD 엔진 — 덮어쓰기 전 보관` 제목으로 그대로 옮긴다. 그 파일은 추가만 하고 고치지 않는다
   - 다른 엔진이 쓴 행은 해소 근거 없이 지우지 않는다. 해소돼 지운 행은 근거를 `갱신 이력`에 적는다
   - `현재` 절 제목에 마지막 갱신 엔진과 병합한 다른 엔진 판을 함께 적는다. 예: `현재 — 2026-10-04 · GPT 갱신(Claude 2026-10-03판 병합)`
4. 사실 값은 복제하지 않고 정본 파일과 claim ID를 가리킨다. 지원현황·README·정본 사이에 서로 다른 말이 보이면 고르지 말고 `열린 문제`에 적는다
5. 맨 아래 `갱신 이력`에 `YYYY-MM-DD 엔진: 요약` 한 줄을 더한다. 지난 `현재` 절은 git 이력으로 남는다
6. 커밋은 사용자가 지시할 때만 한다(Claude는 `/정리` 절차). 이 절차가 커밋을 대신하지 않는다

## 지원 방향

2026-09-23 `공통자료/지원방향.md`를 이 절로 옮겼다.

- PM과 SCM에 번갈아 지원한다. PM은 이력서와 포트폴리오, SCM은 이력서가 기본 구성이다. IT 기술영업 이력서도 `IT기술영업용/`에 보관한다.
- 이력서는 사용자가 양식에 직접 넣을 **내용만 MD로 작성**한다. Word·PDF 생성, 조판, 면접 질문, 시뮬레이션, 추가 보고서는 요청이 없으면 만들지 않는다. 토큰 절약이 우선이다.
- PM 포트폴리오는 공고별 수정 계획을 먼저 누적한다. 사용자가 `PPT 반영`을 지시하면 PPTX를 한 번에 수정하고, PDF는 만들지 않는다.
- 대분류(`PM용/`, `SCM용/`) 바로 아래에는 기본틀과 공고별 폴더를 둔다. `output/`·`source/`는 과거 자료 보관용이다.
- 이력서의 자기소개서는 원 양식의 3단 구조 `방향성 / 성격의 장단점 / 직무 성공 및 실패 사례`를 유지한다.

| 트랙 | 첫 화면에서 설명할 것 | 대표 사례 순서 |
|---|---|---|
| PM | 문제의 근거, 선택과 제외, 정책·요구사항, 운영 검수와 결과 | 범용은 B2B → 관세청. 제품·AI 공고는 마켓빅시 우선 |
| SCM | 발주·공급사·수입·재고 운영과 공급 판단 | 공급운영 → 3PL 통합 → 자료 취합 개선 → 발주 협의 → 통관·B2B·리콜 보조 |
| IT 기술영업 | 현업 업무 이해, 도입 대안 비교, 요구 조율, 적용 확인 | B2B 도입 → 관세청 연동. 신규 고객·수주·매출은 경력으로 만들지 않음 |
